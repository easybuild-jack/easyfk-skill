EasyFK プロジェクトにおいて、プロジェクトの作り方、フレームワークが提供する機能、コードの書き方、既存システムの動き方を AI に伝えます。EasyFK を使っていないプロジェクトでも、フレームワーク非依存の汎用規約だけは利用できますが、能力はかなり制限されます。

> ## まず EasyFK を理解してから、使い方を決めてください
>
> このスイートは [EasyFK アーキテクチャ](https://www.easybuild.pro/easyfk) の解説書です。ここに書かれているモジュール座標、レイヤリング、設定プレフィックス、クラス名とアノテーションは、すべて easyfk フレームワーク自体に由来するもので、一般的な Spring の経験則ではありません。
>
> - **プロジェクトが EasyFK を使っている場合**：すべての機能が利用できます。まず公式サイトで、このアーキテクチャの概要とモジュール一覧を確認してください：**<https://www.easybuild.pro/easyfk>**
> - **プロジェクトが EasyFK を使っていない場合**：利用は可能ですが、フレームワーク非依存の部分のみです — 動く最小限の実装、Alibaba 開発規約、ドキュメントと計画、セルフチェックとレビュー。easyfk 関連の内容（モジュール選定、`easyfk-` 座標とプライベートリポジトリ、フレームワークのクラス名・アノテーション・設定プレフィックス、BOM バージョンによるルーティング、リバース時のフレームワーク解釈）は一切参照せず、適用もしません。
>
> **はっきり言っておきます**：EasyFK を使わない場合、能力は大きく低下します。このスイートの最も価値のある部分は、フレームワークの機能マップと、バージョンごとに正確なクラス名・設定です。それを除くと、残るのは汎用的な開発規約であり、役には立ちますが、汎用の coding skill でも同じものが得られます。

## 1. EasyFK との関係

[EasyFK](https://www.easybuild.pro/easyfk) はエンタープライズ向けの Java 基盤であり、「一度作って全体で再利用する」という位置づけを持ちます。12 のコアモジュール、40 以上のプラガブルコンポーネント、統合された依存関係管理を備え、どのプロジェクトでも作り直すインフラ（統一レスポンス、例外、ログ、認証、ORM、キャッシュ、MQ、スレッドプールなど）を標準コンポーネント化し、業務プロジェクトは必要なものを取り込むだけで開発を始められます。

この AI スキルがアーキテクチャと強く結びついている理由は 3 つあります。

| 理由 | 説明 |
|---|---|
| **フレームワークはクローズドソースで、機能は中にしかない** | `com.mcst:*` の jar はプライベート Maven リポジトリにのみ公開されています。どのモジュールがあるか、クラス名は何か、アノテーションの書き方、設定プレフィックスは何か — AI が一般知識から推測できるものではなく、間違えればコンパイルが通りません |
| **コーディング規約がフレームワークのレイヤリングで決まる** | `Controller → IXxxApi → Service → Repository → Mapper`（および `ApiServerImpl / ApiScImpl / ApiDubboImpl` のマルチスタック実装）は EasyFK の約束事であり、普通の Spring プロジェクトの書き方ではありません |
| **フレームワークが進化し続ける** | easyfk のバージョンによってクラス名、設定項目、モジュール構成が異なります。スキルはプロジェクトが実際に依存する BOM バージョンのスナップショットを読み込むため、そのバージョンで本当に動くコードが書けます |

したがって判断は 2 段階です。

- **`easyfk-` 座標または `com.mcst` パッケージ名がある** → このスイートのすべての規約に従います。
- **ない** → フレームワーク非依存の規約のみを残します：最小限の実装、Alibaba 規約、ログとコメント、ドキュメントと計画、セルフチェックとレビュー、プロジェクト説明の位置づけと業務データ依存。easyfk に関わるモジュール選定、座標とプライベートリポジトリ、クラス名とアノテーション、設定プレフィックス、バージョンルーティングはすべてスキップし、フレームワーク流の書き方を普通の Spring プロジェクトに押し付けません。この場合にできることは限られ、能力は明らかに低下します。もともと EasyFK を使う予定がないなら、汎用の coding skill のほうが適しています。

## 2. 何を解決するか

| スキルがない場合 | スキルがある場合 |
|---|---|
| フレームワークが `Result`、スレッドプール、キャッシュ、ロック、業務番号生成をすでに提供していることを知らず、自前で書いたり、Guava や commons-lang3 など重複する機能を安易に追加したりする | まずフレームワークの機能マップを確認し、既存モジュールがあればそのモジュールドキュメントのクラス名と設定で書き、足りない部分だけを補う |
| レイヤリングが勘頼み：Controller が Service を直接注入する、サービス間呼び出しが契約を経由しない、トランザクションや一意性チェックが抜ける | 規約どおりに層ごとに書く：主キーは `String` + UUID、`@Transactional`、`@SingleUniqueField`、契約 4 点セットを一度に揃え、最後にセルフチェック |
| フレームワーク更新後も AI が古いクラス名と設定プレフィックスを使い続ける | BOM からプロジェクトのバージョンを読み、そのバージョンのドキュメントスナップショットにルーティングし、そのバージョンの API で書く |
| メンテナンスされていない古いプロジェクトを引き継ぎ、コードが読めない | エントリーポイントから 2 つのレポートを逆算する：業務分析レポート + アーキテクチャ分析レポート（フローチャート、シーケンス図、高可用設計を含む） |
| プロジェクトが自分は何で、どのデータに触れているかを説明できず、変更影響を人の記憶に頼る | プロジェクト説明の冒頭に位置づけ（業務プロジェクト / コンポーネントプロジェクト、コンポーネントは誰に提供するかを明記）を書き、第 5 節に業務データ依存の一覧を置く：どの外部データに依存し、どれを自ら管理し、どれを外部に提供するか、それぞれの出所、利用者、変わったときの影響範囲 |
| 自分のコードを自分で確認するため、複雑な変更で分岐や契約同期の漏れが本番まで残る | 複雑な変更や新機能の完了後、開発に参加していない別のサブエージェントを起動し、要件と設計だけを渡してコードを項目ごとにレビューさせる；ブロッキング指摘は修正してから完了とし、タスク状態は計画ドキュメントに反映して上位の管理層が進捗を確認できるようにする |

## 3. 4 つのスキルの役割分担

4 つのスキルは同じ階層に並んでインストールされ、互いを名前で参照します。1 つの要件は通常、そのうち 1 つが主導します。

| スキル | 答える問い | 典型的なトリガー |
|---|---|---|
| [easyfk-framework-skill](easyfk-framework-skill/SKILL.md) | フレームワークに**何があるか**：プロジェクトとモジュール、各モジュールが解く課題、この要件にどのモジュールを選ぶか、既存のユーティリティクラス、設定プレフィックス；あるクラスの**正確なシグネチャ**（メソッドオーバーロード、定数値、設定デフォルト値） | 「MQ を送るにはどのモジュール」「オブジェクト変換の既存ツールはあるか」「easyfk はシャーディングに対応しているか」「`RRBuilder` にはどんなメソッドがあるか」 |
| [easyfk-dev-skill](easyfk-dev-skill/SKILL.md) | コードを**どう書くか**：レイヤリング、命名、各層の書き方、トランザクションと例外、アーキテクチャ系プロジェクトのモジュール分割とスレッドモデル、ドキュメント、セルフチェック | 「注文モジュールにキャンセル API を追加」「easyfk で新規プロジェクトを作る」「starter を書く」 |
| [easyfk-reverse-skill](easyfk-reverse-skill/SKILL.md) | システムが**どうなっているか**：既存コードから業務分析レポート、アーキテクチャ分析レポート、業務データ依存（依存・自管理・外部提供）を復元する | 「この古いプロジェクトの業務フローを整理して」「全体アーキテクチャ図を補って」「このプロジェクトはどの業務データに依存しているか」 |
| [easyfk-generator-skill](easyfk-generator-skill/SKILL.md) | プロジェクトを**どう作るか**：EasyFK バックエンドは `efg`（JDK と `efg` のインストール確認、なければダウンロード・インストールして検証、プロジェクト種別とパラメータを確認、`generator.yml` を書き、CLI を呼び出して生成、成果物を検証）、EasyBuild Admin 管理画面フロントエンドは `easybuild-admin`（プロジェクト名・説明・出力先・パッケージマネージャー・テンプレート版を確認し、`npx` 一発で生成、`package.json` とテンプレート構成を検証） | 「easyfk で注文マイクロサービスを新規作成」「プロジェクトの雛形を生成」「既存プロジェクトにテーブル 1 つの Entity と業務コードを追加」「テーブルの項目が変わったので DTO を更新」「efg がインストールできない / エラーになる」「EasyBuild Admin で管理画面フロントエンドを新規作成」 |

easyfk-dev-skill にはフレームワーク非依存の部分（最小限の実装、Alibaba 規約、ドキュメントと計画、セルフチェックとレビュー）があります。EasyFK を使わないプロジェクトではこの部分だけが利用でき、フレームワーク関連の規約はすべてスキップされ、能力は明らかに低下します。判定方法は §1 を参照してください。

依存関係は一方向です：プロジェクト作成は generator から（generator → フレームワークのバージョン）、コードを書く前にフレームワーク機能を確認（dev → framework）、フレームワーク呼び出しをリバースするときもフレームワークを確認（reverse → framework）。generator はプロジェクトとレイヤードコードを出力するだけで、そのコードをどう書き、どう変えるかは dev が決めます。ただしフロントエンドは例外で、dev の Java レイヤリング規約は適用されません。ページの実装はテンプレート同梱の `docs/开发文档.md` に従います。

## 4. インストール

`SKILL.md` を読む Cursor、Claude Code などの AI コーディングツールに対応しています。4 つのスキルは skills ディレクトリの**第 1 階層**に兄弟ディレクトリとして置く必要があり、`easyfk-skill/` の下にネストすると通常は認識されません。

```bash
git clone --depth 1 https://github.com/easybuild-jack/easyfk-skill.git
```

```powershell
# Windows
powershell -ExecutionPolicy Bypass -File easyfk-skill/install.ps1 [-Target <skills ディレクトリ>]
```

```bash
# macOS / Linux
sh easyfk-skill/install.sh [<skills ディレクトリ>]
```

- インストール先のデフォルトは `~/.cursor/skills`（ユーザー全体）。特定プロジェクトのみなら `<プロジェクト>/.cursor/skills`、Claude Code なら `~/.claude/skills`。
- 同名ディレクトリが既にある場合は削除してからインストールします。改名前の旧 `easyfk-skill`（`name: easyfk-skill`）も併せて削除されます。
- インストール後に IDE を再起動するか、新しいセッションを開いてください。**更新**：再度 clone してインストールスクリプトを実行するだけです。

## 5. 使い方

**スキルを手動で指定する必要はありません。** EasyFK プロジェクトで普段どおりに要件を伝えれば、AI はまずビルドファイル（`easyfk-` 座標）またはソースのパッケージ名（`com.mcst`）から EasyFK プロジェクトだと認識し、BOM バージョンに対応するドキュメントを読み込みます。

EasyFK プロジェクトでない場合はフレームワーク流の書き方を適用せず、汎用規約（最小限の実装、ドキュメントと計画、セルフチェックとレビュー）のみを使い、能力が制限されることを伝えます。普通の Java プロジェクトに `IXxxApi` や `easyfk-` 座標といったフレームワークの約束事を押し付けません。

実際の依頼例：

| 依頼 | 何が起きるか |
|---|---|
| 「easyfk で注文マイクロサービスを新規作成、ローカル MySQL の order データベースに接続」 | JDK と `efg` を確認し、なければダウンロード・インストールして検証 → プロジェクト種別とパラメータを確認 → `generator.yml` を作成 → `efg` を呼び出して生成 → モジュールとレイヤードコードが揃っているか検証 |
| 「EasyBuild Admin で管理画面フロントエンドを新規作成」 | JDK も `efg` も不要：プロジェクト名・説明・出力先・パッケージマネージャーを確認 → `npx easybuild-admin@1.2.0 … --json -y` → `package.json` とテンプレート構成を検証 → `corepack yarn install` / `yarn dev`（ポート 4000、組み込み Mock） |
| 「既存プロジェクトにテーブル 1 つの Entity と業務コードを追加」 | 既存設定を読んで座標とパッケージ名を確認 → `db-tables` に追加 → `efg -m` の後に `efg -s`、手書きファイルは上書きしない |
| 「テーブルの項目が変わったので DTO を更新して」 | テーブル構造を確認 → `efg -d`、DTO と Param のみ変更 |
| 「注文モジュールにキャンセル API を追加、状態チェックとログ出力付き」 | フレームワークに既存機能があるか確認 → レイヤーごとに Controller / Api / Service / Repository 一式を生成 → セルフチェックして変更内容を説明 |
| 「この要件は完了したのでレビューして」 | 開発に参加していないサブエージェントを起動し、要件・設計・変更一覧だけを渡して項目ごとにレビュー、ブロッキング / 提案の一覧を出力；ブロッキングは修正後に再レビューし、結果とタスク状態を計画ドキュメントに記録 |
| 「ここでピークカットが必要。MQ か Disruptor か」 | `mq-*` と `queue-disruptor` の永続化・信頼性の差を比較し、選定と設定プレフィックスを提示。キューを自作しない |
| 「`RRBuilder` にはどんなメソッドがある？」「この設定項目のデフォルトは？」 | その easyfk バージョンの API シグネチャ早見表（モジュール単位、オーバーロード・定数値・設定デフォルトを含む）を参照。記憶で API をでっち上げない |
| 「このプロジェクトは Dubbo と Feign の両方の呼び出しに対応する必要がある」 | マルチスタックのマイクロサービス形態に合わせて契約と実装の分割案を提示 |
| 「この古いプロジェクトはメンテナンスされていない。業務を整理して」 | すべての入口（Controller、MQ コンシューマ、XXL-JOB、Aeron、etcd リーダー選出など）を洗い出す → 業務分析レポート + アーキテクチャ分析レポート + 業務データ依存一覧を出力 |
| 「上流のマーケットデータで契約乗数が変わった。こちらはどこを直す？」 | 業務データ依存一覧のマーケットデータの「利用者」と「変更影響」を確認し、修正が必要なモジュール、インターフェース、`クラス#メソッド` を指摘。リポジトリ全体を検索しない |
| 「新しい easyfk にアップグレードする。どの書き方を変える？」 | 2 つのスナップショットを比較し、改名された設定項目と変更されたクラス名を一覧化。旧記法は残し「バージョン X から変更」と注記 |

## 6. フレームワーク依存

easyfk は**オープンソースではありません**が、無償で利用できます。フレームワークの jar は Maven Central などの公開リポジトリには公開されておらず、公式のプライベート Maven リポジトリから取得します。

リポジトリの URL、アクセストークン、Maven / Gradle の具体的な設定方法は公式サイトを参照してください：<https://www.easybuild.pro/easyfk>

この手順が前提です：リポジトリを設定していないと、`com.mcst:*` の依存はすべて解決に失敗します（アーティファクトが見つからない、または 401）。

- skill の内容を変更する前に、スイートのメンテナンス手順 [easyfk-framework-skill/maintenance.md](easyfk-framework-skill/maintenance.md) を読んでください。easyfk バージョンのドキュメントスナップショットの追加・更新にはそのバージョンのフレームワークソースが必要で、これはメンテナのみが行えます。
- この README を変更するときは、4 つの言語版（`README.md`、`README.zh-CN.md`、`README.zh-TW.md`、`README.ja.md`）をまとめて更新し、章構成と表の行を揃えてください。
- 提出前にローカルで `install.sh` / `install.ps1` を一度実行し、4 つの skill が skills ディレクトリの第 1 階層に正しくインストールされることを確認してください。
- 中国語でも英語でも、どちらの言語での提出も歓迎します。
