# 跨语言互通规约（INTEROP）

本文档面向 **跨语言 SDK 实现者**（Go / C++ / .NET / Rust / Python 等），是 [`aeron协议说明.md`](aeron协议说明.md) 的工程伴随文档：PROTOCOL 定义 wire 字节布局，INTEROP 给出"按规约实现，避免与 Java 参考实现行为漂移"的逐项 checklist。

> **谁应该读**：你正在为本 SDK 写第二种语言的实现；或者你在评估"我们 Go 服务能不能与 Java 服务通过本协议互通"。
>
> **谁不必读**：业务方只用 Java SDK 不涉及第二语言。

> **本文档结构**（原「快速开始 / 互通指南 / 错误码对照」三份已合并为一份）：
> - **快速开始**（下一节，无编号）：30 分钟跑通 Java↔X echo baseline 的 day-1 hands-on。
> - **§0 – §11**：wire / codec / compression / topic / transport / producer-consumer 逐项对齐 checklist + 常见坑。
> - **§12**：跨语言统一错误码对照（metrics label / 诊断字符串）。
> - **附**：互通项目落地建议 + 配套文档。

## 快速开始：30 分钟跑通 Java↔X 互通

本节面向**跨语言 SDK 实施者**（Go / C++ / .NET / Rust SDK 开发者）的 day-1 任务：**在自己机器上 30 分钟内**，跑通 "Java 端 producer → Java 端 consumer" 的 echo baseline，然后用你正在开发的语言对端**替换其中一侧**，做最小互通 verify。跑通后再回到 §1 黄金 verify 路径 7 步走完整流程。

### 快速开始 · 前置

| 工具 | 版本 | 说明 |
|---|---|---|
| JDK | ≥ 17 | 本 SDK 当前 toolchain 锁 17 |
| Git | 任意 | 拉本 repo |
| 你的语言运行时（Go / C++ / Rust / .NET） | — | 至少能跑该语言的 Aeron client binding |
| `xxd` 或类似 hex 查看工具 | — | 看 wire 字节 |
| `aeronmd`（可选，对应 Aeron 的 C 实现 driver） | aeron-c ≥ 1.40 | 不强制；本快速开始默认用 Java embedded driver |

> 💡 **跨语言通信物理层 = Aeron driver 进程**：双端不一定要用同一种语言的 driver，但必须挂到**同一个 driver 进程**（IPC 场景）或**协议兼容的两个 driver**（UDP 场景）。版本要求见 §6.4。

### 快速开始 · Step 1：跑 Java prod / Java cons echo（同进程）

最快验证 SDK 已搭建好的方式。

```powershell
# Windows PowerShell
git clone <repo>
cd aeron
.\gradlew.bat :aeron-examples:run
```

```bash
# Linux / macOS
git clone <repo>
cd aeron
./gradlew :aeron-examples:run
```

入口：[`IpcPingPong.java`](../aeron-examples/src/main/java/com/mcst/aeron/examples/IpcPingPong.java) — 同进程内起 embedded driver + producer + consumer，topic `demo.ping`，发 5 条 `hello-i` 看 consumer 收。

**预期输出**：

```
send  pos=128
send  pos=192
send  pos=256
send  pos=320
send  pos=384
recv  topic=demo.ping  msgIdHigh=...  latency=N us  body=hello-0
recv  topic=demo.ping  msgIdHigh=...  latency=N us  body=hello-1
...（5 条全收）
```

通了 → SDK 编译 + Aeron driver + IPC 通道 + RAW codec 全链路 OK。

### 快速开始 · Step 2：拆成三个 Java 进程跑 IPC（共享 aeronDir）

这一步是**跨语言互通的物理模型**：driver 独立运行，两端各自启 client 挂到同一 `aeronDir`。本 repo `aeron-examples` 已预置三件套，**无需自己写代码**，三个 Gradle task 直接跑：

| 类 | 入口 task | 角色 |
|---|---|---|
| [`StandaloneDriver`](../aeron-examples/src/main/java/com/mcst/aeron/examples/xlang/StandaloneDriver.java) | `:aeron-examples:runXlangDriver` | 独立 driver 进程，占住共享 `aeronDir` |
| [`EchoProducer`](../aeron-examples/src/main/java/com/mcst/aeron/examples/xlang/EchoProducer.java) | `:aeron-examples:runXlangProducer` | 业务 producer，10 条 `hello-i` 发到 `demo.echo` |
| [`EchoConsumer`](../aeron-examples/src/main/java/com/mcst/aeron/examples/xlang/EchoConsumer.java) | `:aeron-examples:runXlangConsumer` | 业务 consumer，订阅 `demo.echo` 打印 |

三件套都接受**第一个位置参数**作为 `aeronDir`（默认 `${java.io.tmpdir}/aeron-xlang`），三个进程必须用**完全一致的字符串**。

**终端 1：起 standalone driver**

```powershell
# Windows PowerShell
.\gradlew.bat :aeron-examples:runXlangDriver
# 或显式指定共享目录（推荐 IPC 性能更好的本地路径）：
.\gradlew.bat :aeron-examples:runXlangDriver --args="C:\Users\$env:USERNAME\AppData\Local\Temp\aeron-xlang"
```

```bash
# Linux / macOS（推荐用 /dev/shm 走 tmpfs）
./gradlew :aeron-examples:runXlangDriver --args="/dev/shm/aeron-xlang"
```

预期输出：

```
standalone Aeron driver up at /dev/shm/aeron-xlang
connect from same machine: DriverManager.external("/dev/shm/aeron-xlang")
press Ctrl+C to stop.
```

终端 1 保持运行（不要关）。

> 💡 **生产替代方案**：用 Aeron 上游 C 实现的 `aeronmd` 二进制（性能更好、依赖更少）：
> ```bash
> # 从 https://github.com/real-logic/aeron/releases 下载 aeron-1.46.7 包
> ./aeronmd -Daeron.dir=/dev/shm/aeron-xlang -Daeron.dir.delete.on.start=true
> ```

**终端 2：起 echo consumer（先起 consumer 避免漏前几条）**

```powershell
.\gradlew.bat :aeron-examples:runXlangConsumer --args="C:\Users\$env:USERNAME\AppData\Local\Temp\aeron-xlang"
```

```bash
./gradlew :aeron-examples:runXlangConsumer --args="/dev/shm/aeron-xlang"
```

预期输出：

```
echo consumer connected to /dev/shm/aeron-xlang, awaiting messages on demo.echo ...
```

**终端 3：起 echo producer**

```powershell
.\gradlew.bat :aeron-examples:runXlangProducer --args="C:\Users\$env:USERNAME\AppData\Local\Temp\aeron-xlang"
```

```bash
./gradlew :aeron-examples:runXlangProducer --args="/dev/shm/aeron-xlang"
```

预期：终端 3 每 500ms 打 `sent[i] pos=... body=hello-i`，终端 2 同步打 `recv  topic=demo.echo  msgIdHigh=...  latency=... µs  body=hello-i`，10 条之后 producer 退出，consumer 与 driver 继续运行。

通了 → 跨进程 / 共享 driver 模型 OK，进入 Step 3 把任一进程换成你的语言对端。

> ⚠️ **Windows 注意**：Windows 没有 `/dev/shm`，用 `%LOCALAPPDATA%\Temp\aeron-xlang` 之类常规目录；Aeron driver / client 自动适配。
>
> 💡 **不传 `--args`** 时三件套都使用 `${java.io.tmpdir}/aeron-xlang`（Linux/macOS 通常是 `/tmp/aeron-xlang`，Windows 是 `%LOCALAPPDATA%\Temp\aeron-xlang`），三个终端只要不传参数就能自动对齐。

### 快速开始 · Step 3：用你的语言替换其中一侧（Java↔X 互通）

**物理层契约（必须双端一致）** —— 详细对齐规则见 §6：

| 项 | Java 端 | 跨语言对端必须 |
|---|---|---|
| `aeronDir` | `/dev/shm/aeron-xlang` | **同一字符串**（IPC 场景） |
| Aeron client major version | `1.52.x` | `1.40+`（详见 §6.4） |
| `channel` URI | `aeron:ipc`（IPC 默认） | **字符串完全一致**，详见 §6.5 ABNF |
| `streamId` | `1001` | **同一整数** |
| `mtuLength` | Aeron 默认 1408 → `maxPayloadLength = 1376` | **同一整数**（详见 §2.5） |

**SDK 层契约（必须实现到位）** —— 索引到本文档对应章节：

| 项 | 实施手册位置 |
|---|---|
| Wire frame 40B header（MAGIC `0x514D4541` LE / VERSION 1 / FLAGS / CODEC_ID / COMPRESSION_ID / TOPIC_LEN / PADDING / PAYLOAD_LEN / TIMESTAMP_NS / MSG_ID_HIGH / MSG_ID_LOW） | [`aeron协议说明.md`](aeron协议说明.md) §3 + §2.2 |
| Topic UTF-8 编码 + 字符集 + 长度 | §5 |
| Codec wire 字节（至少先实现 RAW 跑通 §1 第 1 步） | §3.2 RAW |
| MSG_ID 生成（16 字节，UUIDv7 / Snowflake 任选） | §7.3 |
| 用 Aeron `tryClaim`（**不**用 `offer`） | §7.1 P0 警告 |
| 错误码标准化（metrics label） | §12 |

**黄金 hex 文件自检（强烈推荐）**：在写实际网络对接之前，先用 [`docs/wire-samples/`](wire-samples/) 下 11 个 hex 文件做 **bit-for-bit verify**：

1. 你的语言端 parser 读 `raw-hello.hex` → 应解出：topic=`hello`, codec=RAW, payload=`[0x01,0x02,0x03]`, timestamp=`1700000000000000000`, msgIdHigh=`0x0123456789ABCDEF`, msgIdLow=`0xFEDCBA9876543210`
2. 你的语言端 encoder 用同样固定参数构造 → 输出字节应与 hex 文件**完全等值**

详见 [`docs/wire-samples/README.md`](wire-samples/README.md)。

> ✅ **Java 端 CI 已锁这层契约**：`WireSampleVerifierTest` 每次 CI 跑都拿这 11 个 hex 文件比对 Java 端 `WireSampleExporter` 实时产物；如果 Java 端将来漂移，CI 立刻 fail，黄金文件会强制 commit 更新，你拿到的永远是与 Java 端最新行为一致的字节。

**最小双向 verify（≈ §1 第 1 步）**：跟 Step 2 同样架构（先起 driver，再起业务两侧），把**任一**侧替换成你的语言对端：

| 场景 | Java 端 | 你的语言端 |
|---|---|---|
| 测试 A：跨语言 producer | `:aeron-examples:runXlangConsumer` | 你的语言 producer：发 `topic=demo.echo, payload=byte[]{...}` |
| 测试 B：跨语言 consumer | `:aeron-examples:runXlangProducer` | 你的语言 consumer：订阅 `topic=demo.echo, type=raw bytes` |

两个场景都通 → 双向 RAW 互通完成（即 §1 的 step 1 + step 2），进入剩余 step 3–7 共 5 步：STRING / JSON / SBE Quote / Protobuf 多 type 派发 / LZ4 + Protobuf 大消息。

### 快速开始 · 常见踩坑

| 现象 | 原因 | 修复 |
|---|---|---|
| Java 进程报 `org.agrona.concurrent.AgentTerminationException: ... unknown stream id ...` | 双端 `streamId` 不一致 | 对齐到 `1001` |
| Java consumer 完全收不到（无报错） | `aeronDir` 不同 / channel URI 字符串不一致（比如多了空格、参数顺序不同） | 双端 print URI 字符串对比 |
| Java consumer 报 `FRAME_BAD_MAGIC` | 对端用了 Aeron `offer` 而非 `tryClaim`，导致 wire frame 被自动 fragment | 改用 `tryClaim`，见 §7.1 |
| Java producer 抛 `AeronMqException: frame size N exceeds publication.maxPayloadLength M` | 单帧超过 Aeron `mtuLength - 32` 默认 1376 字节 | 双端同步调大 `mtuLength` + `termBufferLength`，见 §2.5 |
| Java consumer 报 `CODEC_DECODE_FAILED` / `CODEC_ID_MISMATCH` | wire CODEC_ID 与订阅 type 对应的 codec 不一致；或者 codec 字节布局不对 | 拿 `docs/wire-samples/` 黄金文件做单元 verify，见 §12 |
| Windows 上 `MediaDriver` 启动慢 / `/dev/shm` 不存在 | Windows 没有 shared memory 文件系统 | `aeronDir` 用 `%LOCALAPPDATA%\Temp\aeron-...`；启动慢是 Windows fs 特性，不影响功能 |

> 💡 **建议提交节奏**：每通过 §1 一步就提交一个 PR / commit；7 步走完即 v0.1 发布准备就绪。

## 0. 互通保证矩阵

| 维度 | 是否要求双端严格对齐 | 不对齐会怎样 |
|---|---|---|
| Wire frame 头部所有字段 | ✅ 必须 | consumer 拒帧 / 数据破坏 |
| `CODEC_ID` 编号语义 | ✅ 必须 | consumer 走 cross check 失败丢消息 |
| `COMPRESSION_ID` 编号语义 | ✅ 必须 | consumer 解压失败 |
| 各 codec 的具体字节格式（UTF-8 / JSON / Protobuf / SBE 字节） | ✅ 必须（业务约定） | decode 失败 / 字段错位 |
| **Protobuf `.proto` 文件双端共享**（同 git tag） | ✅ 必须 | 字段号 / 类型 drift 导致字段错位、新字段读不到（见 §3.5） |
| **Protobuf 双端 protoc 版本对齐**（同主版本） | ✅ 推荐 | protobuf wire spec 稳定，但 protoc codegen 细节（unknown fields 处理 / builder 接口）可能漂移 |
| **Protobuf 字段号绝不复用**（删字段必须 `reserved`） | ✅ 必须 | 一端解出旧字段值、另一端解出新字段值，业务字段静默错乱 |
| SBE schema XML `byteOrder="littleEndian"` 显式锁定 | ✅ 必须 | 字节序错乱、跨语言完全不通（见 §3.6） |
| SBE 双端 sbe-tool 版本对齐 | ✅ 推荐 | OMG SBE spec 稳定，但工具实现边界差异可能导致 var-data 字节错位（见 [序列化 Codec 接入指南 §1.6.6](序列化Codec接入指南.md)） |
| FORY codec 在跨语言 SDK 中实现 | ❌ **不实现** | 见 §3.7：FORY 仅 Java 内部，跨语言互通用 SBE / Protobuf |
| 各 compression 的具体字节格式 | ✅ 必须 | 解压报错 / 字节流不识别 |
| 字节序 little-endian | ✅ 必须 | 数字字段读出垃圾值 |
| Topic 字符集与长度上限 | ✅ 必须 | 一端发出对端拒 |
| Aeron channel URI / stream id | ✅ 必须（要落在同一 stream） | 物理上根本通不了 |
| MediaDriver 共享方式 | ✅ IPC 必须共享 / UDP 不需要 | IPC 通不了 |
| Producer 的背压策略选择 | ❌ 不需 | 各端独立决策 |
| Consumer 的 dispatch 模式 / dedup 配置 | ❌ 不需 | 各端独立决策 |
| Msg id 生成算法 | ❌ 不需 | consumer 只把 128-bit 当 opaque key |
| Producer 的 topic cache / metrics 实现 | ❌ 不需 | 各端独立实现 |

## 1. 黄金 verify 路径（最小可行互通测试）

任何跨语言 SDK 的"算实现到位"的最小判定 —— 按顺序通过这 7 个互通测试就可以发布预览版：

| # | 测试 | 验证目标 |
|---|---|---|
| 1 | Java prod / 新语言 cons：IPC + RAW codec + `topic = "hello"` + `payload = "hi"`（5 字节） | wire frame header 全字段对齐、topic / payload 字节对齐 |
| 2 | 新语言 prod / Java cons：同上 | 反向 wire 字节对齐 |
| 3 | 双向 STRING codec，含 ASCII + 中文 + emoji 各一条 | UTF-8 边界 |
| 4 | 双向 JSON codec，业务 POJO 含 `int`/`long`/`String`/`boolean`/`array` | JSON 字段命名 + UTF-8 编码 |
| 5 | 双向 **SBE Quote**（fixedLength，schema id=1 templateId=1，body 含 `symbol[8] + int64 price + int32 qty`） | sbe-tool 跨语言 codegen 字节对齐 + messageHeader composite 布局 + littleEndian byteOrder |
| 6 | 双向 **Protobuf 多 type 派发**：同 transport 上注册 `StringValue` + `Int64Value` 各发一条，consumer 端按订阅 type 正确分发 | protobuf 字节互通 + 同 wire `CODEC_ID=2` 多 type 派发（P0 派发逻辑验证）|
| 7 | 双向 LZ4 + Protobuf 大消息（≥10KB） | 压缩 wire 约定 + Protobuf 字节互通 + zip-bomb 防护边界 |

通过这 7 个，剩下的（UDP MDC / dedup / 多 codec 混发 / SBE varLength / ZSTD / DEFLATE / schema 演化）都是同一套机制的延伸，照葫芦画瓢即可。

> **优先级提示**：跨语言互通**主战场是 RAW + STRING + JSON + SBE + PROTOBUF 五种 codec**。SBE / PROTOBUF 是结构化消息的双必选；FORY 不在跨语言 SDK 实施范围（见 §3.7）。

## 2. Wire Frame 逐字段对齐 checklist

参考实现：`com.mcst.aeron.common.frame.{FrameProtocol, FrameEncoder, FrameDecoder}`。

### 2.1 字节序

**统一 little-endian**。即使运行平台是大端机（PPC / MIPS / SPARC），SDK 实现也必须强制 LE。

| 语言 | 推荐 API |
|---|---|
| Go | `encoding/binary.LittleEndian.{PutUint16, PutUint32, PutUint64, Uint16, Uint32, Uint64}` |
| C++ | `htole16 / htole32 / htole64` 或 byte-swap-on-BE |
| Rust | `u32::to_le_bytes() / u32::from_le_bytes()` |
| .NET | `BinaryPrimitives.WriteUInt32LittleEndian` 等 |

**禁止用** "native endian / host endian" API（如 Go `binary.NativeEndian`、C++ 裸 `memcpy` 假设小端、Rust `u32::to_ne_bytes()`），否则会在大端机上挂掉。

### 2.2 字段表（必须逐项对齐）

| 偏移 | 长度 | 字段 | 类型 | 写入策略 | Verify |
|---:|---:|---|---|---|---|
| 0 | 4 | `MAGIC` | 4 字节 ASCII | `'A','E','M','Q'` = wire 上 `0x41 0x45 0x4D 0x51`；按 LE uint32 读 = `0x514D4541` | 拒帧条件：`!= 0x514D4541` |
| 4 | 1 | `VERSION` | uint8 | 当前固定 `0x01` | 拒帧条件：`!= 0x01` |
| 5 | 1 | `FLAGS` | uint8 | bit0=`BATCH`(=0x01) bit1=`COMPRESSED`(=0x02) bit2-7 必须 0 | 若 `COMPRESSION_ID != 0` 必须置位 bit1 |
| 6 | 1 | `CODEC_ID` | uint8 | 取值见 §3 | consumer 据此 cross check |
| 7 | 1 | `COMPRESSION_ID` | uint8 | 取值见 §4 | 0 表示未压缩 |
| 8 | 2 | `TOPIC_LEN` | uint16 LE | `1..255` 字节数；写超会被对端拒 | 拒帧条件：`> 255` |
| 10 | 2 | `PADDING` | uint16 LE | **必须填 0**；未来扩展用 | 解码端不强制校验，但跨语言实现也不能写非 0 |
| 12 | 4 | `PAYLOAD_LEN` | uint32 LE | 压缩**后**的字节数，即 wire 上跟在 topic 后面的字节数 | 拒帧条件：`< 0` 或 `> 2147418072`（即 `Integer.MAX_VALUE - 40 - 0xFFFF` = `2_147_418_072`）<br>**注意**：Java 端用 signed int32 解读，所以最高位的 1（即 `>= 2GB`）实际为负，被拒；跨语言侧用 uint32 也应映射到相同语义 |
| 16 | 8 | `TIMESTAMP_NS` | int64 LE | producer 写入时刻 `epoch_ms * 1_000_000`（Java 端：`System.currentTimeMillis() * 1_000_000L`） | consumer 仅用于 latency 计算，不参与协议判断 |
| 24 | 8 | `MSG_ID_HIGH` | int64 LE | 128-bit 消息 id 高 64 位（opaque） | consumer 仅做 dedup |
| 32 | 8 | `MSG_ID_LOW` | int64 LE | 128-bit 消息 id 低 64 位（opaque） | 同上 |
| **40** | N | `TOPIC` | UTF-8 | 紧接 header，N = `TOPIC_LEN`；字符集严格 §5 | — |
| 40+N | M | `PAYLOAD` | bytes | 紧接 topic，M = `PAYLOAD_LEN`；压缩后字节 | 业务由 codec 解读 |

**整 frame 长度** = `40 + TOPIC_LEN + PAYLOAD_LEN`。

### 2.3 编码侧自检（producer 强制）

1. `frameLength <= Publication.maxPayloadLength()` → 超限拒发（**Aeron 单帧硬约束**，详见 §2.5）；
2. `topicLen` 字段宽度 uint16 但 SDK 限到 `1..255`；
3. `payloadLen` 必须满足 `>=0 && <= MAX_PAYLOAD_LENGTH`（见上表）；
4. 若 `COMPRESSION_ID != 0`，必须同步置位 `FLAGS.bit1`；
5. `PADDING` 写 0；
6. topic 字节经字符集校验后再写入；
7. `tryClaim → commit` 期间一次性写完所有字段；任何中途失败必须 `BufferClaim.abort()` 把帧标 padding。

### 2.4 解码侧自检（consumer 强制，按顺序）

1. `length < 40` → 拒帧（header 不完整）；
2. `MAGIC != 0x514D4541` → 拒帧；
3. `VERSION != 0x01` → 拒帧；
4. `PAYLOAD_LEN < 0` 或 `> MAX_PAYLOAD_LENGTH` → 拒帧；
5. `TOPIC_LEN > 255` → 拒帧；
6. `40 + TOPIC_LEN + PAYLOAD_LEN > length` → 拒帧；
7. 解码 topic、按订阅 Java/Go/C++ type 查 codec（不是按 wire `CODEC_ID`，原因见 §3.5）、按 `COMPRESSION_ID` 查解压器；任一找不到 → 丢消息并上报 `metrics.onError`，**不**抛进 user handler；
8. `codec.codecId() == wire CODEC_ID` → cross check，不等丢消息 + `metrics.onError`。

### 2.5 Aeron 单帧上限（P0：跨语言 producer 必读）

本 SDK Java 端 producer 用 Aeron `Publication.tryClaim`（**不**用 `offer`，原因见 §7.1），所以**整个 wire frame 必须放在单个 Aeron fragment 内**。`tryClaim` 单次上限是 `Publication.maxPayloadLength()` 字节，Aeron 不会自动拆 fragment。超限本 SDK Java 端 producer 提前抛 `AeronMqException: frame size N exceeds publication.maxPayloadLength M`，Go 端实现应该对齐这个语义（提前 fail，不要让 Aeron 回 `MAX_POSITION_EXCEEDED` 神秘错误码）。

**`maxPayloadLength` 公式**（Aeron 上游定义）：

```
maxPayloadLength = mtuLength - 32   // 32 = Aeron DataHeaderFlyweight.HEADER_LENGTH
```

`mtuLength` 由 Aeron driver 启动参数 / channel URI 控制：

| 默认 | 数值 | 说明 |
|---|---|---|
| Aeron UDP 默认 `mtuLength` | `1408` | 适合标准以太网 MTU 1500，留 60 字节给 IP + UDP 头；`maxPayloadLength = 1408 - 32 = ` **`1376` 字节** |
| Aeron IPC 默认 `mtuLength` | `1408` | 与 UDP 默认相同（Aeron driver 不会因为 IPC 就自动调大）；同样 `maxPayloadLength = 1376` 字节 |
| 业务自定义 | 由 channel URI `mtu=...` 或 driver 启动属性 `aeron.mtu.length` / `aeron.ipc.mtu.length` 覆盖 | — |

> ⚠️ **跨语言陷阱**：很多业务方第一反应是"我消息 10KB，怎么默认就拒了？" —— 这是 Aeron 的硬约束，**不是本 SDK 的限制**。出错信息明示 "调大 `termBufferLength` 或拆分消息"，但更精确的做法是同步调大 `mtuLength`（见下）。

**要发更大单帧的合规做法**——**V1 SDK 仅支持方案 2（driver 启动期全局调大）**：

1. **driver 启动期全局调大**（V1 SDK 当前唯一方案，影响所有 publication）：
   ```
   -Daeron.mtu.length=8192             # UDP, 默认 1408
   -Daeron.ipc.mtu.length=65536        # IPC, 默认 1408
   -Daeron.term.buffer.length=2097152            # UDP term, 默认 16M
   -Daeron.ipc.term.buffer.length=8388608        # IPC term, 默认 64M
   ```
   `term.buffer.length` 必须 2 的幂且 ≥ `8 × mtu.length`；**双端 driver 必须配置完全一致**，否则 Aeron driver 启动期就拒绝 publication / subscription。Java 端可通过 JVM 启动参数 `-D...` 或 `MediaDriver.Context.mtuLength(int)` / `.ipcMtuLength(int)` / `.publicationTermBufferLength(int)` / `.ipcPublicationTermLength(int)` 编程式设置；Go 端 `aeron.Context.MtuLength(int32)` + driver 端 system property 同名属性对齐。

2. **per-publication 调大**（即在 channel URI 里写 `?mtu=64k|term-length=2m`）：Aeron 上游原生支持，但 **V1 本 SDK 的 `ChannelSpec` 暂未暴露 `mtu` / `term-length` 字段**（见 [`ChannelSpec.toAeronUri()`](../aeron-common/src/main/java/com/mcst/aeron/common/config/ChannelSpec.java) 只输出固定 3 种 URI），且 §6.5 ABNF 也未包含这两字段。要 per-publication 隔离需求请提 issue 升级到 V2。

> 💡 **整 message 上限的另一个公式**：Aeron 完整 message 上限（含自动 fragment 拆分时）= `min(16 MB, termBufferLength / 8)`。**但本 SDK 用 `tryClaim` 强制单 fragment，所以这个公式对本 SDK 不适用**；实际限制就是上面的 `maxPayloadLength = mtuLength - 32`。

**业务层分片**（**强烈不推荐**）：本 SDK 不做自动 fragment 拆分；如果业务消息超大，业务方自己拆 + 自己组（含丢失 / 乱序重组），跨语言双端实现一致性极难维护。优先用方案 1 调大 mtu。

**跨语言端必查项**：Go SDK 实施时**driver 端**必须协商 `aeron.mtu.length` / `aeron.ipc.mtu.length` / `aeron.term.buffer.length` / `aeron.ipc.term.buffer.length` 与 Java 端 driver 完全一致；client 端用 `aeron.Context.MtuLength(int32)` 等 API 对齐 publication 期望。

## 3. Codec 跨语言对齐

### 3.1 ID 表

| ID | 名称 | Java 类 | wire 格式 |
|---:|---|---|---|
| 0 | `RAW` | `RawBytesCodec` | payload 字节即业务字节 |
| 1 | `SBE` | `aeron-codec-sbe` + 业务 schema codegen | 业务侧定义（详见 §3.6） |
| 2 | `PROTOBUF` | `ProtobufCodec<T extends MessageLite>` | 标准 protobuf wire（`SerializeToArray` 输出，详见 §3.5） |
| 3 | `JSON` | `JsonCodec<T>` (Jackson) | UTF-8 JSON 字节 |
| 4 | `STRING` | `StringCodec` | 纯 UTF-8 字节 |
| 5 | `FORY` | `aeron-codec-fory` (`ForyCodec<T>`) | Apache Fory wire（详见 §3.7） |
| 6..99 | — | 预留 | — |
| 100..255 | 用户自定义 | 业务实现 `Codec` SPI | 业务约定 |

### 3.2 RAW (0)

最简单，无任何包装。

**Verify**：
- Java 发 `byte[] {0x01, 0x02, 0x03}` → 跨语言端 payload 收到字节 `01 02 03`，长度 3。
- 反向同理。

### 3.3 STRING (4)

UTF-8 字节，**无长度前缀、无 null 终结符**。Java 实现：`new String(bytes, StandardCharsets.UTF_8)` / `s.getBytes(StandardCharsets.UTF_8)`。

**Verify**：
- 发 `"hello"` → 5 字节 `68 65 6C 6C 6F`
- 发 `"中文"` → 6 字节 `E4 B8 AD E6 96 87`
- 发 `""` → `PAYLOAD_LEN = 0`，payload 区空（Java 端 `encodedLength("") == 0`）
- 发 `null` → Java 端 `encodedLength(null) == 0`；跨语言端实现可选支持 `nil/null`，建议同样映射到空 payload

### 3.4 JSON (3)

Java 默认使用 `new ObjectMapper()`，**未配置任何 SerDe / 命名策略**，所以：
- 字段名 = Java 类字段名（默认 camelCase）
- `int` / `long` / `String` / `boolean` / `null` 按 JSON 标准
- 字符串 UTF-8
- 无 BOM、无 pretty print
- 字段顺序 = Java 类声明顺序（Jackson 默认）

**业务方双端必须共享字段命名约定**：
- Go 端用 `encoding/json` 默认是 PascalCase（导出字段），必须用 `json:"camelCaseName"` tag 与 Java 端对齐
- C++ / Rust 各自的序列化库都要注意命名策略
- 推荐：双端都从同一份 JSON Schema / OpenAPI spec 生成 DTO 类

**Verify**：
- Java POJO `class User { String name; int age; }` 发 `new User("alice", 30)` → wire 字节 = `{"name":"alice","age":30}` 的 UTF-8 bytes
- Go 端 struct `type User struct { Name string \`json:"name"\`; Age int \`json:"age"\` }` 必须能解出 `{alice, 30}`

### 3.5 PROTOBUF (2) — ✅ 跨语言双必选（兼容现存业务）

Google Protocol Buffers v3（也支持 v2）。**生态最成熟、跨语言最广泛**：protoc 官方支持 Java / C++ / Go / Python / C# / Rust / Dart / Ruby / PHP 等 10+ 语言，wire format 长期稳定（spec 已固定多年）。

> **本 SDK 跨语言互通的双必选 codec 之一**：与 SBE 并存、按场景分工：
>
> | 场景 | 推荐 |
> |---|---|
> | 已有 Protobuf 业务消息、跨语言 RPC 风格 | **Protobuf** |
> | 新业务、低延迟广播、行情 / tick | **SBE** |
>
> 详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §0 完整选型表。

**Wire 字节布局**：

```
+-------------------------+-------------------+----------------------------------+
| broadcast frame (40 B)  | topic (1..255 B)  | PAYLOAD = protobuf wire bytes    |
+-------------------------+-------------------+----------------------------------+
                                              |<--- frame.PAYLOAD_LEN bytes  -->|
```

protobuf wire 由 [protobuf 官方 spec](https://protobuf.dev/programming-guides/encoding/) 标准化（tag = 字段号 << 3 | wire type；递归编码）。Java 端 `MessageLite.toByteArray()` / Go 端 `proto.Marshal(value)` / Python 端 `value.SerializeToString()` 输出字节**完全一致**——这是 Protobuf 跨语言最强的地方。

**强制对齐契约**：

1. **业务方双端必须共享同一份 `.proto` 文件**（同 git tag）。推荐独立 `proto-schemas` repo + git submodule / 包发布，**绝不**拷贝 `.proto` 到各业务 repo（drift 是必然）。详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2.7.3。
2. **同 codec 家族多业务 type 派发**（与 SBE/FORY 一致，**P0 警告**）：
   - wire `CODEC_ID = 2` 只标识"这是 Protobuf 家族"，**不能**区分具体 message type（`OrderProto` / `TradeProto` 共享同一个 wire id）
   - consumer 端 codec 派发主键必须用 **订阅时声明的业务 type**（Java 端是 `Class<T>`，Go 端是 `reflect.Type` 或注册时的 token）
   - wire `CODEC_ID` 仅做 cross check：consumer 拿到的 codec instance 的 `codecId()` 必须等于 2，否则配对错误丢消息
   - 跨语言 SDK 实现这条派发逻辑**至关重要**（Java 端漏了这条要花 7 轮 review 才修复 P0）
3. **protoc 版本对齐**：protobuf wire 跨工具版本兼容性极强，但建议双端锁定到下表中的对齐版本（详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2.7.2）：

   | 语言 | 运行时库 | 推荐版本 |
   |---|---|---|
   | Java | `com.google.protobuf:protobuf-java` | **3.25.5**（本 SDK 当前对齐） |
   | Go | `google.golang.org/protobuf` （new API） | v1.34+ |
   | C++ | `libprotobuf` | 3.25.x |
   | Python | `protobuf` PyPI | 4.25+ |
   | C# | `Google.Protobuf` NuGet | 3.25+ |
   | Rust | `prost` crate | 0.13+ |

   ⚠️ Go 端**不要**用 `github.com/golang/protobuf`（old API，已 deprecated 多年）；用 `google.golang.org/protobuf`。

4. **proto3 优先于 proto2**（向后兼容更可控；proto2 `required` / `optional` 跨语言演化坑较多）。
5. **schema 演化遵守 protobuf 官方规则**（详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2.6.3）：
   - 加字段：✅ 向后兼容（老 consumer 把新字段当 unknown 字段）
   - 删字段：⚠️ 删后字段号**绝不能复用**（用 `reserved 5;` 显式占位）
   - 改字段类型：❌ 不兼容，必须改字段名 + 分配新字段号

**Verify**（按 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2.7.6 完整 7 步）：

- 业务 `.proto`：`message User { string name = 1; int32 age = 2; }`
- Java 发 `User.newBuilder().setName("alice").setAge(30).build()` → Go 端用同一份 .proto 解出 `{alice, 30}`，反之亦然
- 同时注册 `User` 和 `Order` 两个 protobuf type 各发一条，两端都要正确分发到对应订阅 handler（P0 派发验证）
- 黄金 hex 文件：[`docs/wire-samples/pb-stringvalue-alice.hex`](wire-samples/) + [`docs/wire-samples/pb-int64value-30.hex`](wire-samples/)（验证同 wire id 多 type 派发）

详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2。

### 3.6 SBE (1) — ✅ 跨语言双必选（低延迟场景首选）

本 SDK 的 `aeron-codec-sbe` 是**泛型适配框架**，**不持有任何业务 schema**。业务方在公司独立的 `sbe-schemas` repo 维护 `.xml` schema，用 sbe-tool 跑 codegen，双端各自得到 `XxxEncoder` / `XxxDecoder` 类。

> **为什么 SBE 是本 SDK 跨语言双必选中"低延迟场景的首选"**：与 Aeron 同源（LMAX real-logic 出品）；wire 格式由 OMG 标准化、跨工具实现一致；sbe-tool 官方支持 Java / C++ / C# / Go / Rust target，**同一份 schema codegen 出来的字节天然 bit-for-bit 互通**；schema 强治理（XML 文件，git 版本化）；zero-copy 友好。
>
> SBE 与 PROTOBUF 是**并存的双必选**（详见 §3.5）—— 新业务高频低延迟广播优先 SBE，兼容现存业务 / 通用 RPC 风格消息用 PROTOBUF。

**Wire 字节布局**：

```
+-----------------------------+-----------------------+
| messageHeader composite (8) | message body (N bytes)|
+-----------------------------+-----------------------+
```

`messageHeader` composite 严格 8 字节，字段顺序固定（schema 中写在 `<composite name="messageHeader">` 里）：

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---:|---:|---|---|---|
| 0 | 2 | `blockLength` | uint16 LE | message body 固定部分长度（不含 var-data） |
| 2 | 2 | `templateId` | uint16 LE | 业务 message 类型 id（如 `<sbe:message id="1">` 即 1） |
| 4 | 2 | `schemaId` | uint16 LE | schema 全局 id（如 `<sbe:messageSchema id="1">` 即 1） |
| 6 | 2 | `version` | uint16 LE | schema 版本（用于向后兼容的字段新增） |

整段（`messageHeader` + body）就是本 SDK 帧上的 `PAYLOAD`。

**强制对齐契约**：

1. **schema XML 顶层必须 `byteOrder="littleEndian"`**：SBE schema 允许写 `bigEndian`，但本 SDK 协议规约统一 little-endian；schema 端必须显式锁定，否则跨语言会出现字节序错乱。
2. **同 codec 家族多业务 type 派发**（与 PROTOBUF/FORY 一致）：
   - wire `CODEC_ID = 1` 只标识 SBE 家族，**不区分具体 message type**（`Quote` / `Trade` / `OrderBook` 共享同一个 wire id）
   - consumer 端派发主键必须用 **订阅时声明的业务 type**（Java 端是 `Class<T>`，Go 端是 `reflect.Type` 或注册时的 token）
   - wire `CODEC_ID` 仅做 cross check：consumer 拿到的 codec instance 的 `codecId()` 必须等于 wire `CODEC_ID = 1`
   - 跨语言 SDK 实现这条派发逻辑**至关重要**（Java 端漏了这条要花 7 轮 review 才修复 P0）
3. **schema 必须严格一致**：双端使用相同的 `.xml` 文件（同 `schemaId` / `schemaVersion`），通过 git submodule / artifact 引入；schema drift 会导致字段错位或反序列化失败。
4. **sbe-tool 版本对齐**：Java 端用 sbe-tool 1.32.x；Go 端使用对应版本的 sbe-go codegen。OMG SBE spec 稳定，但工具实现的边界处理（如 var-data 对齐字节）可能有差异，建议锁版本，详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §1.6.6。
5. **fixedLength vs varLength 是 SDK 内部优化，wire 层不可见**：Java 端 `SbeCodec.fixedLength(...)` / `varLength(...)` 是性能取舍，wire 字节由业务 lambda 严格按 sbe-tool 输出写入，对端不需要区分。

**Verify**：

- 业务 schema：`<sbe:messageSchema id="1" byteOrder="littleEndian"><sbe:message name="Quote" id="1"><field name="symbol" type="symbolType"/><field name="price" type="int64"/><field name="qty" type="int32"/></sbe:message></sbe:messageSchema>`
- Java 发 `new Quote("AAPL", 18742L, 100)` → wire payload = 8 字节 messageHeader (`14 00 01 00 01 00 00 00`) + 20 字节 body (`41 41 50 4C 00 00 00 00 36 49 00 00 00 00 00 00 64 00 00 00`) = 28 字节
- Go 端用同一份 schema codegen 出来的 `QuoteDecoder.Decode(buf)` 应解出 `{symbol="AAPL", price=18742, qty=100}`
- 反向：Go 发 → Java 收，wire 字节应完全一致

详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §1。

### 3.7 FORY (5) — ❌ 跨语言不推荐（仅 Java 内部）

> **本 SDK 跨语言互通路线不包含 FORY**。Java 端保留 `aeron-codec-fory` 作为"纯 Java 服务的零配置 POJO 接入"路径（详见 [`Aeron 组件使用手册.md`](Aeron%20组件使用手册.md) §17.5 方式 C）；跨语言场景（Go / C++ / Rust SDK）**只需实现 RAW / STRING / JSON / PROTOBUF / SBE 五种 codec**，FORY 在跨语言 SDK 中可保留 `CODEC_ID = 5` 枚举但不实现 codec body（收到 FORY 帧时统一按"未注册 codec"丢消息上报 `metrics.onError`）。
>
> 为什么不做：① Apache Fory 跨语言 binding（fory-go / fory-cpp）跟进 Fory 上游有 lag；② Fory XLANG wire 还在演进，跨语言一致性不如 SBE / Protobuf 稳定；③ 业务方真正需要跨语言时用 SBE（高性能结构化）或 Protobuf（通用）已经覆盖了 Fory 的全部场景。

Apache Fory 是高性能多语言序列化框架，**wire 格式取决于 Fory 实例的 Language 模式**：

- **`Language.JAVA` 模式（默认）**：wire 字节包含 Java 类元数据（class hash、字段布局），**仅 Java 端可反序列化**。即便对端跑 Apache Fory 的 Python/Go/Rust 实现，也读不出来。适用于"我只发给 Java consumer"的场景，性能最优（比 JSON 快 20~50x）。
- **`Language.XLANG` 模式**：wire 由 Apache Fory 跨语言协议定义，可被 Python / Go / Rust / C++ 等任何 Fory 实现反序列化。本 SDK 帧头 `CODEC_ID = 5` 标识 FORY 家族，payload 段即 Apache Fory XLANG wire。

**对齐契约（XLANG 模式）**：
- 双端必须使用相同主版本的 Apache Fory 实现（wire 跨次版本兼容由 Apache Fory 项目自己保证，本 SDK 不背书）
- 双端 `register(Class, typeId)` 的 `typeId` 必须完全一致；本 SDK 的 `ForyCodec.Builder` 在 `crossLanguage(true)` 时强制要求每个 `register` 调用提供 `typeId` 或 `typeName`，缺一即 `build()` 失败
- 类字段名 / 类型必须在双端结构等价；Fory XLANG schema 演化策略详见 [Apache Fory 官方跨语言文档](https://fory.apache.org/docs/guide/xlang/)

**`Language.JAVA` 模式跨语言警告**：
- wire `CODEC_ID = 5` 在两种模式下相同，**仅靠帧头无法区分 JAVA / XLANG**
- 若 producer 用 JAVA 模式发，consumer 用 XLANG 模式收（或反过来），SDK 不会拦截，最终在 Fory 内部反序列化时抛 `CodecException`
- 跨语言互通场景**只能用 XLANG 模式**，本 SDK 不为 JAVA 模式 wire 提供跨语言 SDK

**同 codec 家族多业务 type 派发**（与 PROTOBUF/SBE 一致）：
- wire `CODEC_ID = 5` 只标识 FORY 家族，不区分具体 type
- consumer 端 codec 派发主键仍是订阅 `Class<T>`，wire `CODEC_ID` 只做 cross check

**Verify（XLANG 模式）**：
- 业务双端各自构 `ForyCodec.builder(Order.class).crossLanguage(true).typeId(101).build()`
- Java 发 `new Order("AAPL", 100, 187.42, ["nyse","vip"])` → Python / Go 端 Apache Fory `register(Order, 101)` 后能 deserialize 出等值对象

详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §3。

**跨语言 SDK 实现建议**：

- Codec 枚举里保留 `FORY = 5`（与 Java 端 `CodecIds.FORY` 对齐）
- 默认**不**注册任何 `Codec<T>` for FORY 家族
- 收到 wire `CODEC_ID = 5` 的帧时按"未注册 codec"路径处理：丢消息 + `metrics.onError(CODEC_NOT_FOUND)`，不抛进 user handler
- 若业务方明确要跨语言 Fory，自行实现 `Codec` 接口包 Apache Fory binding（属业务自定义扩展，不在 SDK 内置范围）

## 4. Compression 跨语言对齐

### 4.1 ID 表

| ID | 名称 | wire 格式 |
|---:|---|---|
| 0 | `NONE` | payload 字节即业务字节，不压缩 |
| 1 | `LZ4` | `[4 字节 LE uint32 originalLength][lz4 block bytes]` |
| 2 | `ZSTD` | zstd frame format（自带原始长度，无前缀） |
| 3 | `DEFLATE` | raw deflate stream（**无 zlib header / 无 ADLER32**） |

### 4.2 NONE (0)

`PAYLOAD_LEN` 字节就是业务 codec 输出的字节，不做任何包装。

### 4.3 DEFLATE (3) — ⚠️ **第一个大坑**

Java 实现：`new Deflater(Deflater.DEFAULT_COMPRESSION, /*nowrap=*/true)` + `new Inflater(/*nowrap=*/true)`。`nowrap=true` 表示 **raw deflate stream，没有 zlib 的 CMF/FLG 头部和 ADLER32 尾部**。

跨语言对应 API（**关键：用 `flate`，不用 `zlib`**）：

| 语言 | 用 | 不用 |
|---|---|---|
| Go | `compress/flate.NewWriter` / `compress/flate.NewReader` | ❌ `compress/zlib`（自带 zlib header） |
| Rust | `flate2::write::DeflateEncoder` / `flate2::read::DeflateDecoder` | ❌ `ZlibEncoder` / `GzEncoder` |
| C++ (zlib) | `deflateInit2(stream, level, Z_DEFLATED, /*windowBits=*/-15, ...)` | ❌ `deflateInit(...)`（默认带 zlib wrap） |
| .NET | `System.IO.Compression.DeflateStream` | ❌ `ZLibStream`（.NET 6+ 自带 zlib wrap） |

`windowBits = -15` 或 `nowrap=true` 是 raw deflate 的关键开关。

**Verify**：
- Java prod 压缩 `"aaaaaaaaaaaaaaaaaaaa".getBytes()`（20 字节 'a'）→ wire payload ≈ 6 字节左右（具体值依 zlib 版本）
- Go cons 用 `flate.NewReader` 解压拿到同样的 20 字节 'a'
- 若 Go 端误用 `zlib.NewReader`，会报 `zlib: invalid header` —— 这是最常见的诊断信号

### 4.4 LZ4 (1) — ⚠️ **第二个大坑**

Java 实现：`net.jpountz.lz4.LZ4Factory.fastestInstance().fastCompressor()`，输出是 **lz4 block format**（不是 lz4 frame format）。

**Wire 字节布局**：

```
+-----------------------------+-----------------------------+
| 4-byte LE uint32 origLen    | lz4 block bytes             |
+-----------------------------+-----------------------------+
```

第一段是**未压缩字节数**的 LE uint32（让 decompressor 预分配输出 buffer 防 zip-bomb）。**这是本 SDK 自定义的约定，不是 lz4 协议本身的字段**。

第二段是 lz4 block format 输出（无 magic 字节、无 checksum、无 frame header）。

跨语言对应 API（**关键：用 block API，不用 frame API**）：

| 语言 | 用 | 不用 |
|---|---|---|
| Go | `github.com/pierrec/lz4/v4.CompressBlock` / `UncompressBlock` | ❌ `lz4.NewWriter` / `lz4.NewReader`（输出带 frame header 的字节流） |
| Rust | `lz4_flex::block::compress` / `decompress_size_prepended` 也行（自带 4 字节长度前缀，且也是 LE，但需 verify 实际字节兼容） | ❌ `lz4_flex::frame` |
| C++ | `LZ4_compress_default` / `LZ4_decompress_safe` | ❌ `LZ4F_compressFrame` / `LZ4F_decompress` |
| .NET | `K4os.Compression.LZ4.LZ4Codec.Encode` / `Decode` | ❌ `LZ4Stream` |

**Verify**（producer 侧）：
```
encode payload = "hello"   (5 bytes)

wire payload (Java 端):
  bytes[0..3] = 05 00 00 00      (LE uint32 = 5, originalLength)
  bytes[4..]  = lz4 block format bytes for "hello"
```

跨语言实现读取时：先读 4 字节 LE 拿 `originalLength`，再把 `wire[4..]` 喂给 lz4 block decompressor，预期输出长度等于 `originalLength`。

### 4.5 ZSTD (2)

Java 实现：`com.github.luben.zstd.Zstd.compressByteArray(...)`，输出标准 zstd frame format（含 magic `0x28 B5 2F FD` + frame header + 原始长度元信息 + 压缩 block）。

跨语言对应 API（都是标准 zstd frame，互通无障碍）：

| 语言 | 用 |
|---|---|
| Go | `github.com/klauspost/compress/zstd.{NewWriter, NewReader}` 或 `Encoder.EncodeAll` / `Decoder.DecodeAll` |
| Rust | `zstd::stream::encode_all` / `decode_all` 或 `zstd::block::*` |
| C++ | `ZSTD_compress` / `ZSTD_decompress`（libzstd） |
| .NET | `ZstdNet.Compressor` / `Decompressor`（NuGet） |

**Verify**：
- Java prod 压缩 `"hello world"` → wire bytes 第一个 4 字节是 zstd magic `28 B5 2F FD`
- Go cons 用 `zstd.NewReader` 解压拿到原文

**注意**：Java 端用 `Zstd.getFrameContentSize` 探得原始长度后做 dstCapacity 防 zip-bomb；跨语言实现也应实现等价的"先探长度再分配"逻辑，否则恶意发送方可以构造小压缩字节但巨大解压输出的 zip bomb。

### 4.6 压缩库版本兼容矩阵

跨语言对端使用的压缩库版本不必完全等同 Java 端（压缩算法 wire 格式由各 spec 标准化，库版本只影响实现质量 / 性能），但建议参考下表挑选**已知兼容**的版本：

| 算法 | Java 端依赖 | Java 端版本 | Go 推荐 | C++ 推荐 | Rust 推荐 | .NET 推荐 |
|---|---|---|---|---|---|---|
| **LZ4** | `org.lz4:lz4-java` | **1.8.0**（lz4 block format wire 标准） | `pierrec/lz4/v4` 4.1+（用 `CompressBlock` / `UncompressBlock`，**不**用 frame API）| libzstd `lz4.h` `LZ4_compress_default` / `LZ4_decompress_safe` | `lz4_flex` 0.11+ block API | `K4os.Compression.LZ4` 1.3+ block API |
| **ZSTD** | `com.github.luben:zstd-jni` | **1.5.6-3**（zstd 1.5.6 + jni wrapper rev 3） | `klauspost/compress/zstd` v1.17+ | libzstd 1.5.6+ | `zstd` crate 0.13+ | `ZstdNet` 1.4+ |
| **DEFLATE** | JDK 内置 `java.util.zip.Deflater(nowrap=true)` | JDK 17 标准库 | `compress/flate`（标准库，**不**用 `compress/zlib`） | zlib `deflateInit2(... windowBits=-15 ...)` | `flate2` 1.0+ raw deflate | `System.IO.Compression.DeflateStream`（**不**用 `ZLibStream`） |

**兼容性策略**：

1. **LZ4**：本 SDK wire 协议自定义"4 字节 LE 长度前缀 + lz4 block"，不依赖 lz4 frame format；任何支持 lz4 block API 的库都能互通。lz4-java 1.8.0 输出的 block 字节是 lz4 spec 标准产物，与 C 实现的 lz4 r130+ 兼容（已稳定 10+ 年）。
2. **ZSTD**：zstd frame format 由 RFC 8478 标准化，跨实现互通无障碍。Java 端版本号 `1.5.6-3` 中前段（`1.5.6`）= zstd C 库版本，后段（`-3`）= jni binding rev；wire 兼容性看前段，与跨语言对端 zstd 库主版本对齐即可。
3. **DEFLATE**：raw deflate stream（RFC 1951）。**跨语言最大坑：选错 wrapper**。zlib 的 `Deflater` 默认带 zlib wrapper（CMF/FLG header + ADLER32 trailer，RFC 1950）；本 SDK Java 端用 `nowrap=true` 显式去掉 wrapper，跨语言端必须对齐：
   - 用 raw deflate API（如 Go `compress/flate`、Rust `flate2::write::DeflateEncoder`、C `deflateInit2(..., -15, ...)`、.NET `DeflateStream`）
   - **不**用 zlib API（如 Go `compress/zlib`、Rust `flate2::write::ZlibEncoder`、C `deflateInit(...)`、.NET `ZLibStream`）—— 跨语言对端拿到字节会报 `invalid zlib header`

**回归路径**：跨语言新 SDK 集成新版压缩库时，过 §1 黄金 verify 路径第 7 步（LZ4 + Protobuf 大消息）即认为字节级互通。同时验证 ZSTD / DEFLATE 各一条（用 1KB 重复 'a' 测试样本即可）。

## 5. Topic 跨语言对齐

### 5.1 字符集

**严格 ASCII 子集**：`[A-Za-z0-9.\-_]`，即：
- 大写字母 `A-Z`（0x41..0x5A）
- 小写字母 `a-z`（0x61..0x7A）
- 数字 `0-9`（0x30..0x39）
- 字符 `.`（0x2E）`-`（0x2D）`_`（0x5F）

**禁止**：所有非 ASCII（中文 / emoji / 重音符号）、`/`、`:`、`@`、空格、控制字符。

为什么这么严：
- 保证 byte length == char count，简化长度校验
- 避开 Aeron channel URI 转义冲突
- 保证日志 / 指标 / Prometheus label 可读

### 5.2 长度

**`1..255` 字节**（即 1..255 ASCII 字符）。空 topic 禁止；`> 255` 字节的帧解码端必须丢弃。

### 5.3 编码

直接按字节写入。Java 端 `Topic.validateAndEncode` 实现是 `(byte) charAt(i)`（字符集已限 ASCII，等价于 UTF-8 编码）。跨语言实现可以用 ASCII / UTF-8 任一，结果一致。

### 5.4 匹配

**精确字节匹配**。**不支持** 通配符 / 前缀匹配 / regex（V1 显式不做）。consumer 维护订阅的 topic 集合，逐字节比对。

## 6. Aeron 传输层对齐

跨语言互通的物理基础：双端必须挂到**同一个 Aeron stream**。

### 6.1 Channel URI

业务方必须双端用**字符串完全一致**的 channel URI。Java 端通过 `ChannelSpec` 构造：

| 场景 | URI（producer & consumer 完全一致） | 互通条件 |
|---|---|---|
| 同机 IPC | `aeron:ipc` | 双端必须挂同一个 MediaDriver（共 aeronDir）|
| UDP unicast | `aeron:udp?endpoint=10.0.0.5:40456` | consumer 必须知道 producer 的 IP:port |
| UDP MDC（多接收方动态加入） | `aeron:udp?control=10.0.0.5:40456\|control-mode=dynamic` | MDC 模式下 producer / consumer 用**完全相同** URI；Aeron driver 内部处理 control endpoint 协商，consumer 不需要单独指定自家 endpoint |

跨语言 SDK 必须支持构造与 Java 端 `ChannelSpec.toAeronUri()` 输出**字符串完全一致**的 URI（包括 `?` `=` `|` 分隔符、字段顺序、无多余空格）。Java 参考实现见 `com.mcst.aeron.common.config.ChannelSpec`。

**唯一例外：订阅专属参数 `tether`。** IPC 订阅端可以写 `aeron:ipc?tether=false`（SDK 侧 `ChannelSpec.ipcUntethered()`），用来脱钩慢订阅——Aeron 默认 tethered，publication 的写入上限取最慢订阅的位置，一个活着但不消费的订阅会顶住所有订阅者；untethered 订阅落后超窗口时由 driver 摘除、稍后从最新位置重新加入，自己丢帧不连累别人。此时 producer 仍是 `aeron:ipc`，两端 URI 字符串**不一致**，但落点仍是同一 Aeron stream：streamId 展开按 `transportUri()`（去掉订阅专属参数后的传输端点 URI）计数，见 §6.2 与 §7.4.3。除 IPC 外的通道本 SDK 未暴露 `tether`。

### 6.2 Stream ID

默认 `1001`。整数，双端必须一致。所有 topic 都走同一个 stream id，topic 过滤在 SDK 层（frame header 的 `TOPIC` 字段）做。

多 partition（`channels` 列表里同一传输端点出现多次）时，streamId = `baseStreamId` + 该端点在列表中**此前出现的次数**。计数键是 `ChannelSpec.transportUri()`，即**不含 `tether` 等订阅专属参数**的传输端点 URI；因此 producer 配 `aeron:ipc`、consumer 配 `aeron:ipc?tether=false` 时，两端的 partition 0 都落在 `baseStreamId`，不会错位。展开算法见 §7.4.3。

### 6.3 MediaDriver 共享

| 传输 | MediaDriver 共享要求 |
|---|---|
| IPC | **必须共享同一 MediaDriver 进程**，即双端 Aeron client 用同一个 `aeronDir`（如 `/dev/shm/aeron-shared`）|
| UDP unicast | 各端独立 MediaDriver 即可，通过网卡通信 |
| UDP MDC | 同 UDP unicast |

跨语言 IPC 互通的部署模型：
- 启动一个独立的 MediaDriver 进程（Java 或 C 客户端都可以启），共享 `aeronDir`
- Java 业务进程 `DriverManager.external("/dev/shm/aeron-shared")` 挂上去
- Go 业务进程也连同一个 aeronDir 启 Aeron Go client

### 6.4 Aeron 版本

Java 端当前依赖 Aeron `1.52.1`（见 `settings.gradle` 的 version catalog）。跨语言 SDK 用的 Aeron 客户端版本应与之**协议兼容**（major 版本一致）。Aeron 的 wire protocol 在 1.x 内向后兼容，1.40+ 都能互通。

### 6.5 Channel URI 形式化 grammar

跨语言 SDK 必须能生成与 Java 端 `ChannelSpec.toAeronUri()` **字符串完全一致**的 URI（参考 `com.mcst.aeron.common.config.ChannelSpec`）。当前 V1 SDK 支持以下四种 channel 的形式化 grammar（ABNF 风格）：

```abnf
channel-uri    = ipc-uri / ipc-untethered-uri / udp-unicast-uri / udp-mdc-uri

ipc-uri        = "aeron:ipc"
ipc-untethered-uri = "aeron:ipc?tether=false"          ; 仅 subscription(consumer) 端

udp-unicast-uri = "aeron:udp?endpoint=" host-port
udp-mdc-uri     = "aeron:udp?control=" host-port "|control-mode=" control-mode

control-mode   = "dynamic" / "manual"                  ; V1 SDK 仅生成 "dynamic"

host-port      = host ":" port                         ; host 形式见下
host           = ipv4-literal / ipv6-bracketed / dns-hostname
port           = 1*5DIGIT                              ; 1..65535
```

**字段顺序约束**（严格按下表，跨语言 SDK 实现时不可调整）：

| URI | 字段顺序 | 示例 |
|---|---|---|
| IPC | （无字段） | `aeron:ipc` |
| IPC untethered（仅订阅） | `tether` | `aeron:ipc?tether=false` |
| UDP unicast | `endpoint` | `aeron:udp?endpoint=10.0.0.5:40456` |
| UDP MDC | `control` → `control-mode` | `aeron:udp?control=10.0.0.5:40456\|control-mode=dynamic` |

> `ipc-untethered-uri` 只改变订阅端的 tether 行为，**不改变传输端点**：参与 streamId 计数的仍是 `aeron:ipc`（`ChannelSpec.transportUri()`）。starter 在 producer 侧配到它会启动期直接报错（该参数对 publication 无意义）。跨语言 SDK 若不实现该参数，Java 侧配了 `tether=false` 的 consumer 与它的 producer 仍能互通——`tether` 是订阅专属参数，不参与 Aeron 的 publication/subscription 匹配，只影响本端订阅行为。

**禁止行为**（跨语言 SDK 必须避免）：

- ❌ 字段间多余空格或换行
- ❌ URL-encode 等号 / 分隔符
- ❌ 大小写差异（必须全小写 `aeron:` / `endpoint=` 等）
- ❌ 字段顺序与上表不同（即便 Aeron driver 能解析，本 SDK 跨端字符串等值比对会失败）
- ❌ trailing `\n` / `\r` / 空格
- ❌ 引号包裹 host:port

**V1 SDK 未涵盖但 Aeron 自身支持的字段**（业务方可通过自定义 `ChannelSpec` 扩展，跨语言对端需相应扩展才能互通）：

- `term-length` / `mtu` / `tags` / `linger` / `reliable` / `ttl` / `interface` / `init-term-id`
- `session-id` / `eos`（producer 控制）
- `group` / `rejoin` / `tether=true`（subscription 控制；`tether=false` 已在 V1 支持的 `aeron:ipc?tether=false` 中覆盖，其它通道未暴露）

若业务方使用了 V1 SDK `ChannelSpec` 之外的字段，**跨语言对端必须按字符串完全一致原则同步实现**。建议向 SDK 提 issue / PR 把字段加入 `ChannelSpec` 统一管理，避免字段顺序 / 字符串格式漂移。

## 7. Producer / Consumer 行为对齐

### 7.1 Producer 端

**必须对齐**：
- frame header 各字段（§2）
- topic 字符集校验（§5）
- frame 大小不超过 `Publication.maxPayloadLength()`，超限拒发（详见 §2.5 数值 + 调大方法）
- 同 codec 家族多 type 发送时，wire `CODEC_ID` 必须一致
- **🔴 P0：使用 Aeron `tryClaim` 接口，禁止用 `offer`**（详见下方"P0 警告"）

**不必对齐**：
- 背压策略（4 选 1，是 producer 自家事务）
- msg id 生成算法（Java 是 Snowflake，跨语言可以用 UUIDv7 / TSID / 自家中心化生成，只要 16 字节即可）
- topic UTF-8 cache 实现
- ThreadLocal / 内存池策略

> 🔴 **P0 警告：producer 必须用 Aeron `Publication.tryClaim`，不能用 `offer`**
>
> **为什么**：
> - 本 SDK wire frame 是一个**不可分割的整体**（含 40B header + topic + payload），consumer 端按帧解析。
> - Aeron `offer` 在 frame 长度 > `maxPayloadLength` 时会**自动 fragment 拆分**，对端 `FragmentAssembler` / `ImageFragmentAssembler` 会按 Aeron 自家协议重组；这跟本 SDK frame 协议**不在同一层**，对端按本 SDK FrameDecoder 解第一片就会拒帧（`length < 40` 或 `MAGIC` 错）。
> - `tryClaim` 在长度 > `maxPayloadLength` 时**抛 `IllegalArgumentException`**（提前 fail），符合本 SDK 期望——把"消息过大"暴露为业务错而不是 Aeron 内部协议事故。
>
> **Java 端参考实现**：
> ```java
> long result = publication.tryClaim(frameLen, claim);
> if (result > 0) {
>     // 在 claim.buffer() 上一次性写完 40B header + topic + payload，最后 claim.commit()
> } else {
>     // 走背压策略：result 是 Aeron 负数原因码（NOT_CONNECTED / BACK_PRESSURED / ADMIN_ACTION / CLOSED / MAX_POSITION_EXCEEDED）
> }
> ```
> 参见 `com.mcst.aeron.producer.AeronProducer.doSend`。
>
> **Go 端对齐**：使用 `aeron-go` 的 `Publication.TryClaim(length int32, bufferClaim *logbuffer.Claim) int64`，**不要**用 `Publication.Offer(buffer *atomic.Buffer, offset, length int32, ...) int64`。
>
> **跨语言双向 verify**：§1 黄金 verify 路径第 1 步（IPC + RAW + "hi"）即可命中——如果 Go 端用了 `offer`，Java 端 consumer 会按 `FRAME_BAD_MAGIC` 拒帧（错误码见 §12.2.1）。

### 7.2 Consumer 端

**必须对齐**：
- frame header 解码 / 校验（§2.4）
- topic 精确匹配
- codec 派发主键用**订阅时声明的业务 type**，不用 wire `CODEC_ID`
- wire `CODEC_ID` 做 cross check
- 解压器按 `COMPRESSION_ID` 查找
- 类型不匹配 / codec 找不到 / 解压失败 → 永不向 user handler 抛错，统一进 metrics

**不必对齐**：
- dispatch 线程模型（INLINE / 工作池）
- dedup 算法（环形 hash / Bloom / 不去重）
- metrics 实现

### 7.3 Msg id

128-bit，consumer **只把 (high, low) 当 16 字节 opaque key 做 dedup**，不解释内部字段语义。

跨语言 producer 生成 msg id 的最低要求：**在合理时间窗（如 1 小时）内全局不撞**。可选方案：
- Snowflake（Java 当前实现）
- UUIDv7（时间排序 + 随机）
- TSID
- 集中式 ID 服务

### 7.4 分片跨语言实现要点（v1.0+）

> 用法见 [`Aeron 组件使用手册.md`](Aeron%20组件使用手册.md) §13，实现以源码 `com.mcst.aeron.common.partition`（`PartitionLayout` / `Murmur3Partitioner` / `NoKeyStrategy`）为准。本节只列跨语言对齐 checklist。

#### 7.4.1 wire 仍然不变

按 [`docs/aeron协议说明.md` §1.1](aeron协议说明.md#11-分片--分组不进-wire)：分片 / 分组完全是部署期拓扑维度，**不写进任何 frame 字段**。一个 partition 在 wire 上等于"该 partition 对应的 `(channelUri, streamId)` 元组所承载的 Aeron stream"。

#### 7.4.2 选择是否实现分片

| 方案 | 实现复杂度 | 跨语言互通 |
|---|---|---|
| **A：跨语言 SDK 不实现分片**（推荐 v1） | 极低 | 跨语言端只暴露单 partition 接入 API；与 Java 多 partition 端互通时，部署期约定它接入哪一个 `(channelUri, streamId)` |
| **B：跨语言 SDK 完整实现分片** | 中 | 必须复刻 PartitionLayout + Murmur3 + NoKeyStrategy；跨语言 producer / consumer 才能与 Java 多 partition 端字节级对齐 |

绝大多数情况下选 A 即可。

#### 7.4.3 选 B 时的字节级对齐

如果跨语言 SDK 选择实现完整分片：

1. **`PartitionLayout` 展开规则**（源码 `com.mcst.aeron.common.partition.PartitionLayout`）的伪代码必须按位等价：
   ```
   seen = {}
   for i in 0..N-1:
       transport = channels[i].transportUri()      // 传输端点 URI：不含 tether 等订阅专属参数
       uri       = channels[i].toAeronUri()        // 实际建 publication / subscription 用的 URI
       streamId  = baseStreamId + seen.getOrDefault(transport, 0)
       emit Slot(partitionId=i, channelUri=uri, streamId=streamId)
       seen[transport] = seen.getOrDefault(transport, 0) + 1
   ```
   **计数键必须是 `transportUri()` 而不是 `toAeronUri()`**：订阅端给 `aeron:ipc` 加 `?tether=false` 后完整 URI 变了，若按完整 URI 计数，consumer 的 partition 0 会算出与 producer 不同的 streamId（此前 SDK 用的就是完整 URI，会导致 untethered consumer 一条都收不到）。
   验证：用 [`PartitionLayoutTest.java`](../aeron-common/src/test/java/com/mcst/aeron/common/partition/PartitionLayoutTest.java) 同一组输入跑跨语言端，每个 slot 的 `(channelUri, streamId)` 必须完全相同。

2. **Murmur3Partitioner 哈希**字节级匹配：用 [`Murmur3PartitionerTest.java`](../aeron-common/src/test/java/com/mcst/aeron/common/partition/Murmur3PartitionerTest.java) 的固定向量（key 字节序列 → partitionId）做对照。
   - key 转字节：`String` → UTF-8；`byte[]` 原样；`long` / `int` / 其它原始类型 → ?（**跨语言侧需要先与 Java 端协商一种规范化策略**，例如统一转 UTF-8 字符串、或仅支持 `byte[]`/`String` 两种 key 类型。Java 端当前用 `Object.toString()` 是默认行为，跨语言生产建议 key 类型限定为 `byte[]` / UTF-8 `String` 以避免 toString 实现差异）。

3. **NoKeyStrategy** 跨语言可选实现，最简实现选 `FIRST`（永远 partition 0）即可。`ROUND_ROBIN` 跨实例计数器各自独立，**跨语言端的轮询计数与 Java 端无对齐要求**（每个 producer 实例自己轮）。

4. **Partitioner 抛异常的处理**：自定义 partitioner 抛异常时不要直接 propagate 到 user code；统一捕获并按 `metrics.onError(topic, partition=-1, throwable)` 上报，当条消息丢弃。

#### 7.4.4 静态分组消费

`groupId` / `partitionAssignment` 完全是 consumer 实例本地配置：
- **`groupId` 仅作 metrics tag**，不进 wire；跨语言侧自由实现
- **`partitionAssignment` 决定本实例订哪些 `(channelUri, streamId)`**；跨语言 consumer 可以选只订一个 partition（最简实现）
- 同 group 内多实例的"完全覆盖 + 互不重叠"约束由部署期人工保证；推荐复刻 [`Cluster.validateAssignments`](../aeron-common/src/main/java/com/mcst/aeron/common/partition/Cluster.java) 的校验逻辑作为部署 hook

### 7.5 错误码标准化

跨语言 SDK 端内错误分类（frame 解码 / codec / compression / dispatch / producer backpressure ...）的**诊断字符串 + metrics label** 必须按 §12 错误码对照 对齐，让运维 / 监控在多语言部署下能跨端 group by。

**必须对齐**：
- 错误分类名（`FRAME_BAD_MAGIC` / `CODEC_ID_MISMATCH` / `DECOMPRESS_FAILED` ...）
- metrics 上报时带 `error.code` label
- 日志格式建议带 `error.code` 前缀

**不必对齐**：
- 异常类继承结构（Java 端 `FrameDecodeException` / `CodecException` 等）
- 错误诊断 message 的具体文案（前缀对齐即可）

## 8. 常见坑总览（按发现顺序）

| # | 坑 | 触发条件 | 诊断信号 |
|---|---|---|---|
| 1 | 字节序写成 native | 大端机部署 | 数值字段读出错乱（如 `PAYLOAD_LEN` 异常大被拒帧） |
| 2 | MAGIC 写成 `0x41454D51`（big-endian 视角） | 用 BE 写 int32 | consumer 全量拒帧，metrics 上 `errors` 暴涨 |
| 3 | DEFLATE 用了 zlib 库（带 header） | 用 `compress/zlib` 而非 `compress/flate` | 解压报 `invalid header` / `unexpected EOF` |
| 4 | LZ4 用了 frame 库 | 用 `lz4.NewWriter` 而非 block API | 解压报 `unknown magic` |
| 5 | LZ4 漏写 4 字节 LE 长度前缀 | 直接把 lz4 block 当 payload | Java 端 `lz4 payload too short to carry length prefix` |
| 6 | TOPIC_LEN > 255 没拒 | wire 字段宽 uint16，实现按 65535 上限 | 一端能发，对端拒帧；行为不对称 |
| 7 | Topic 字符集放宽（如允许 `/`） | 用了 MQTT 风格 topic | 一端能编码，对端 `topic contains illegal character` |
| 8 | JSON 字段命名不一致 | Go 端没加 `json:"name"` tag | 字段全 null / 类型不匹配 |
| 9 | Protobuf .proto 文件版本漂移 | 双端 codegen 不是同一份 schema | 字段错位、新字段读不到 |
| 10 | Codec 派发按 wire `CODEC_ID` 走 byId 派发 | 多 protobuf / SBE type 注册到同一个 byId 槽 | 只有最后注册的 type 能收到，其他全丢（Java 端 P0 历史教训）|
| 11 | IPC 双端没共享 MediaDriver | 各起一个 driver，aeronDir 不同 | 物理层根本通不了，`isConnected()` 永 false |
| 12 | Channel URI 字符串不一致 | UDP MDC 一端写 `dynamic` 一端写 `manual` | 物理层通不了 |
| 13 | Stream ID 不一致 | 双端默认值不同 | 物理层通不了 |
| 14 | Producer `FLAG_COMPRESSED` 与 `COMPRESSION_ID` 不一致 | 压缩了但忘置 flag | 跨语言实现按 flag 判断时漏走解压路径 |
| 15 | `TIMESTAMP_NS` 用 epoch ns 直接 read（int64） | 假定永远正数 | 2262 年后会回绕负数；可忽略 |
| 16 | `MSG_ID_HIGH/LOW` 字段被实现成 `uint64` | 与 Java `long`（signed）不一致 | dedup 哈希计算行为不一致；msg id 比对值不变所以实际可用，但内部表征要小心 |
| 17 | zip bomb 防护漏掉 | 没设 `dstCapacity` 上限 | 恶意 prod 发送 1KB 压缩字节解出 1GB 把 cons 内存爆 |
| 18 | **SBE schema XML 漏写 `byteOrder="littleEndian"`** | sbe-tool 默认其实是 littleEndian，但 schema 没显式锁定，被同事改成 `bigEndian` 没人发现 | 一端按 LE 编，另一端按 BE 解，所有数值字段全乱（symbol 字段看起来 OK 因为是 ASCII 字节序无关）|
| 19 | **SBE messageHeader composite 字段顺序不对** | 业务 schema 写 `<composite name="messageHeader">` 时把字段顺序写成 `templateId, blockLength, ...` | 跨语言互通时 blockLength / templateId 读出来互换，consumer 完全无法识别 message type |
| 20 | **SBE 双端 sbe-tool 版本差异过大** | Java 端 1.32.x，Go 端用了 5 年前的 sbe-go fork | OMG spec 主体兼容，但 var-data 对齐字节 / enum 编码细节可能漂移，定长消息能通 var-data 消息断（罕见，但难诊断）|
| 21 | **SBE schema 双端不一致** | 一端用 v1.0，另一端用 v1.1（加了字段） | 老 consumer 用 schema v1.0 解新 v1.1 帧，按 `blockLength` 截断不读新字段（OK）；新 consumer 用 schema v1.1 解老 v1.0 帧，应回退到默认值（业务方在 decoder lambda 里手动按 `version()` 分支处理，漏处理就读到垃圾）|

## 9. 互通验证策略

### 9.1 单元层级（在每个语言 SDK 内做）

1. **Frame 字节对照**：手工构造一条已知字节序列的 frame，喂 decoder 应解出已知字段
2. **每个 codec 的 round-trip**：encode → bytes → decode → assertEqual
3. **每个 compression 的 round-trip**：随机字节 → compress → decompress → assertArrayEquals
4. **越界 / 异常输入**：MAGIC 错、VERSION 错、topic 过长、payload 长度错、压缩字节损坏 → 全部应拒帧

### 9.2 端到端（跨语言）

最有效的方式：**黄金样例文件**（hex dump）。

由 Java 参考实现一次性导出一批 "标准 wire 字节"，跨语言 SDK 实现者拿这些文件直接做：
- decode：能解出预期字段
- re-encode：给同样的业务输入，输出 wire 字节应该 bit-for-bit 等于 hex dump 文件

例如 `docs/wire-samples/` 目录下：

```
wire-samples/
├── raw-hello.hex                       # RAW codec, topic="hello", payload=[0x01,0x02,0x03]
├── string-ascii-hello.hex              # STRING codec, payload="hello"
├── string-utf8-chinese.hex             # STRING codec, payload="中文"
├── string-emoji.hex                    # STRING codec, payload="🚀"（4 字节 UTF-8）
├── json-user.hex                       # JSON codec, payload={"name":"alice","age":30}
├── sbe-quote-fixed.hex                 # SBE fixedLength Quote (symbol=AAPL price=18742 qty=100)
├── sbe-orderbook-var.hex               # SBE varLength OrderBookSnapshot（含 repeating group）
├── sbe-multi-template-pair.hex         # 同 transport 上 Quote + Trade 两条（同 schemaId 不同 templateId）
├── pb-multi-type-pair.hex              # 同 transport 上 StringValue + Int64Value 两条
├── lz4-1kb-repeating.hex               # LZ4 压缩，1KB 重复 'a'
├── zstd-1kb-repeating.hex              # ZSTD 同上
└── deflate-1kb-repeating.hex           # DEFLATE 同上
```

由 `:aeron-examples:exportWireSamples` Gradle 任务一次性导出（见仓库 `docs/wire-samples/README.md`）。跨语言 SDK 实现端拿到这批文件后做"读 + 重编 bit-for-bit 等值"是验证 wire 层互通的最高效手段。

### 9.3 物理层（同机/跨机）

按 §1 黄金 verify 路径跑过即认为 SDK 实现到位。

## 10. 兼容性策略

跨语言 SDK 演进时遵守同一套兼容性规则（见 [`aeron协议说明.md`](aeron协议说明.md) §14）：

| 变更 | 兼容性 | 处理 |
|---|---|---|
| 增加 `CODEC_ID` / `COMPRESSION_ID`（仍在保留段） | 向后兼容 | 旧 consumer 找不到注册表项即丢消息 + `metrics.onError`，业务不应感知 |
| 增加 `FLAGS` 高位 bit | **不兼容** | 必须 bump `VERSION`；旧 consumer 见非 0x01 拒帧 |
| 调整 header 字段顺序 / 长度 | **不兼容** | 必须 bump `VERSION` |
| 调整某个 codec 内部字节格式（如 LZ4 长度前缀长度变成 8 字节） | **不兼容** | 必须 bump `VERSION` |
| 调整 topic 字符集 / 长度上限 | 收紧不兼容 / 放宽建议 bump `VERSION` | — |

## 12. 错误码对照（INTEROP-ERROR-CODES）

本节定义跨语言 SDK 间**统一的错误分类与诊断字符串**，让运维 / 监控 / metrics 聚合在多语言部署下能跨端对齐。§7.5 的错误码标准化要求即以本节为准。

> **谁应该读**：实现新语言 SDK 时，按本表把内部错误映射到统一的 `ErrorCode` 枚举；业务方做跨语言部署运维时，按本表对齐告警规则 / Prometheus label。

### 12.1 设计原则

1. **wire 层不传错误码**：本协议的 wire frame 是单向 broadcast，不带 ACK / 错误回传。错误码仅作用于**端内** metrics + 日志，不跨语言传输。
2. **错误是端内事件**：每端独立分类、独立上报 metrics（Java 端 `ConsumerMetrics.onError(topic, partition, groupId, throwable)` / `ProducerMetrics.onError(topic, partition, throwable)`），跨语言聚合靠**字符串对齐**（class 名 / message 前缀 / Prometheus label）。`partition` / `groupId` 在单 partition 部署下分别恒为 `0` / `null`。
3. **不强制错误码 ID**：不引入像 HTTP status 一样的数字码，因为这会绑定 SDK 内部细节。**对齐的是诊断字符串前缀**，跨语言对端可以照搬。
4. **可观测优先**：每个错误都应该有一致的 `error.code` label，方便 Prometheus group by。

### 12.2 Consumer 端错误码

#### 12.2.1 Frame 解码（消息进入前）

来源：`com.mcst.aeron.common.frame.FrameDecoder.decodeHeader(...)` 抛 `FrameDecodeException`。

| 错误码 | 触发条件 | Java message 前缀 | metrics label | 业务影响 |
|---|---|---|---|---|
| `FRAME_TOO_SHORT` | `length < 40` | `frame too short for header: <N>` | `error.code="FRAME_TOO_SHORT"`, topic=`<unknown>` | 该 fragment 丢，user handler 不感知 |
| `FRAME_BAD_MAGIC` | `MAGIC != 0x514D4541` | `bad frame magic: 0x<hex>` | `error.code="FRAME_BAD_MAGIC"`, topic=`<unknown>` | 同上；通常是 stream 串了或对端 SDK bug |
| `FRAME_UNSUPPORTED_VERSION` | `VERSION != 0x01` | `unsupported frame version: <N>` | `error.code="FRAME_UNSUPPORTED_VERSION"`, topic=`<unknown>` | 同上；预示 producer 升到 V2 而 consumer 没跟 |
| `FRAME_PAYLOAD_LEN_OUT_OF_RANGE` | `PAYLOAD_LEN < 0` 或 `> MAX_PAYLOAD_LENGTH` | `payload length out of range: <N>` | `error.code="FRAME_PAYLOAD_LEN_OUT_OF_RANGE"`, topic=`<unknown>` | 同上；可能是字节序错（如对端按 BE 写了 LE 字段）|
| `FRAME_TOPIC_LEN_EXCEEDS_LIMIT` | `TOPIC_LEN > 255` | `topic length <N> exceeds SDK limit 255` | `error.code="FRAME_TOPIC_LEN_EXCEEDS_LIMIT"`, topic=`<unknown>` | 同上 |
| `FRAME_DECLARED_LEN_EXCEEDS_AVAILABLE` | `40 + TOPIC_LEN + PAYLOAD_LEN > fragment_length` | `declared frame length <N> exceeds available <M>` | `error.code="FRAME_DECLARED_LEN_EXCEEDS_AVAILABLE"`, topic=`<unknown>` | 同上；通常是 Aeron 层 fragment 不完整或 wire 损坏 |

#### 12.2.2 Topic 过滤（消息已通过 frame 解码）

| 错误码 | 触发条件 | 行为 |
|---|---|---|
| `TOPIC_NOT_SUBSCRIBED` | consumer 未订阅该 topic | 静默丢，**不**报 error metric（这是常态：fan-out 上别人订的 topic）|
| `MSG_DUPLICATE` | dedup 命中 | 走 `metrics.onDuplicate(topic, partition, groupId)`，**不**走 `onError` |

#### 12.2.3 Codec / Compression 派发

| 错误码 | 触发条件 | Java message 前缀 | metrics label | 业务影响 |
|---|---|---|---|---|
| `CODEC_NOT_FOUND_FOR_TYPE` | consumer 订阅了 `Class<T>` 但 codec 注册表里没有对应条目（且 fallback resolver 也返回 null） | `no codec for type <FQN>` 或 `CodecException: no codec for type ...` | `error.code="CODEC_NOT_FOUND_FOR_TYPE"`, topic=`<topic>` | 该 topic 该消息丢；user handler 不感知 |
| `CODEC_ID_MISMATCH` | consumer 解出的订阅 codec 的 `codecId()` ≠ wire `CODEC_ID` | `wire codec id <X> does not match subscribed type <FQN> (registered codec id = <Y>) on topic <topic>` | `error.code="CODEC_ID_MISMATCH"`, topic=`<topic>` | 该消息丢；通常是 producer / consumer codec 配对错误（一端用 JSON 编 Order，另一端订 Order 但注册的是 Protobuf codec）|
| `CODEC_DECODE_FAILED` | `codec.decode(...)` 抛 RuntimeException | （codec 自身异常的 message，如 Protobuf `InvalidProtocolBufferException` / SBE `IndexOutOfBoundsException` / JSON `JsonProcessingException`） | `error.code="CODEC_DECODE_FAILED"`, topic=`<topic>` | 该消息丢；通常是 wire 字节损坏或 schema drift。**Protobuf 专项排查**：① 双端 `.proto` 文件是否同 git tag（80% 概率根因）；② 字段号是否被复用（在 `.proto` 里 grep `reserved` 看历史）；③ protoc 版本主版本是否一致（Java 端 protoc 3.25.x ↔ Go `protoc-gen-go` v1.34+ / C++ libprotobuf 3.25.x，跨主版本可能出 unknown wire type）；④ 检查 `optimize_for = LITE_RUNTIME` 是否一端启用了 lite runtime 另一端没有。详见 [`序列化Codec接入指南.md`](序列化Codec接入指南.md) §2.6.3 / §2.7.2 |
| `COMPRESSION_NOT_FOUND_FOR_ID` | wire `COMPRESSION_ID` 在 consumer 注册表找不到 | `no compression for id <N> on topic <topic>` | `error.code="COMPRESSION_NOT_FOUND_FOR_ID"`, topic=`<topic>` | 该消息丢；通常是 producer 启用了 LZ4 但 consumer 没引入 `aeron-compression-lz4` 模块 |
| `DECOMPRESS_FAILED` | `decompressor.decompress(...)` 抛 RuntimeException，且达到 `maxDecompressedBytes` 上限仍失败 | `decompress failed on topic <topic> (cap=<N>): <cause>` | `error.code="DECOMPRESS_FAILED"`, topic=`<topic>` | 该消息丢；可能是字节损坏 / zip-bomb 防护命中 / 跨语言对端用错 wrapper（如 zlib 而非 raw deflate）|

#### 12.2.4 Dispatch（已成功 decode，进 user handler 前）

| 错误码 | 触发条件 | Java message 前缀 | metrics label | 业务影响 |
|---|---|---|---|---|
| `DISPATCH_FAILED` | user handler 自身抛 RuntimeException 没吞住 | （user handler 异常 message） | `error.code="DISPATCH_FAILED"`, topic=`<topic>` | 该消息已上报 `metrics.onReceived(...)` 算"接收成功"；handler 异常不影响下条消息 |

### 12.3 Producer 端错误码

| 错误码 | 触发条件 | Java exception 类 | metrics label | 业务影响 |
|---|---|---|---|---|
| `TOPIC_INVALID_CHARACTER` | topic 含非 `[A-Za-z0-9.\-_]` 字符 | `IllegalArgumentException("topic contains illegal character ...")` | `error.code="TOPIC_INVALID_CHARACTER"` | `send()` 抛业务异常 |
| `TOPIC_TOO_LONG` | topic 字节长度 > 255 | `IllegalArgumentException("topic too long: ...")` | `error.code="TOPIC_TOO_LONG"` | 同上 |
| `TOPIC_EMPTY` | topic 长度 = 0 | `IllegalArgumentException("topic must not be empty")` | `error.code="TOPIC_EMPTY"` | 同上 |
| `CODEC_NOT_FOUND_FOR_TYPE` | producer `send(topic, value)` 时 `value.getClass()` 没注册 codec | `CodecException: no codec for type ...` | `error.code="CODEC_NOT_FOUND_FOR_TYPE"` | `send()` 抛业务异常 |
| `CODEC_ENCODE_FAILED` | `codec.encode(...)` 抛 RuntimeException | （codec 自身异常 message） | `error.code="CODEC_ENCODE_FAILED"` | `send()` 抛业务异常；wire 没产生 |
| `CODEC_LENGTH_MISMATCH` | SBE varLength 路径 `encodedLength` vs `encode` 输出字节数不一致 | `CodecException: codec wrote <X> bytes but declared <Y>` | `error.code="CODEC_LENGTH_MISMATCH"` | `send()` 抛业务异常；`BufferClaim.abort()` 把 frame 标 padding |
| `COMPRESSION_FAILED` | `compressor.compress(...)` 抛 RuntimeException | （compression 库异常 message） | `error.code="COMPRESSION_FAILED"` | `send()` 抛业务异常 |
| `FRAME_TOO_LARGE_FOR_PUBLICATION` | `40 + topicLen + payloadLen > Publication.maxPayloadLength()` | `IllegalArgumentException("frame too large for publication: ...")` | `error.code="FRAME_TOO_LARGE_FOR_PUBLICATION"` | `send()` 抛业务异常 |
| `PUBLICATION_BACKPRESSURED` | `tryClaim` 返回 `BACK_PRESSURED`（后续按 backpressure 策略处理：DROP / BLOCK / RETRY / ERROR）| `BackpressureException`（仅 ERROR 策略时） | `error.code="PUBLICATION_BACKPRESSURED"` | 取决于 backpressure 策略 |
| `PUBLICATION_NOT_CONNECTED` | `tryClaim` 返回 `NOT_CONNECTED` | （不抛，进入 retry） | `error.code="PUBLICATION_NOT_CONNECTED"` | 等下次连接 |
| `PUBLICATION_CLOSED` | `tryClaim` 返回 `CLOSED` | `IllegalStateException("publication closed")` | `error.code="PUBLICATION_CLOSED"` | `send()` 抛业务异常 |
| `PUBLICATION_MAX_POSITION_EXCEEDED` | `tryClaim` 返回 `MAX_POSITION_EXCEEDED` | `IllegalStateException("publication max position exceeded")` | `error.code="PUBLICATION_MAX_POSITION_EXCEEDED"` | `send()` 抛业务异常；通常需重连 |
| `PUBLICATION_ADMIN_ACTION_RETRYABLE` | `tryClaim` 返回 `ADMIN_ACTION`（短时 retry 后仍未消除）| `BackpressureException` 或自定义 | `error.code="PUBLICATION_ADMIN_ACTION_RETRYABLE"` | 同 BACK_PRESSURED |

### 12.4 Lifecycle / 注册 / 启动期错误

| 错误码 | 触发条件 | Java exception 类 | 业务影响 |
|---|---|---|---|
| `SUBSCRIBE_TOPIC_DUPLICATE` | 同一 consumer 重复订阅同 topic | `IllegalStateException("topic already subscribed: <topic>")` | `subscribe()` 抛；fail-fast |
| `SUBSCRIBE_TYPE_NOT_REGISTERED` | 订阅时 `Class<T>` 在 codec 注册表找不到（fallback 也未提供）| `IllegalStateException("no codec registered for subscribed type: ...")` | `subscribe()` / `start()` 抛 |
| `SUBSCRIBE_WITHOUT_CONSUMER` | `@AeronTopic` 方法存在但 `easyfk.config.aeron.consumer.enabled = false` | `IllegalStateException("@AeronTopic methods found but consumer is disabled ...")` | starter 启动期 fail-fast |
| `DRIVER_NOT_AVAILABLE` | producer / consumer build 时关联的 driver 已关闭 | `IllegalStateException("driver not available")` | builder 抛 |
| `DRIVER_VERSION_MISMATCH` | 端 client 与 driver Aeron 版本不兼容 | Aeron 自身的 `AeronException` | client 启动期抛；版本要求见 §6.4 |

### 12.5 跨语言对齐策略

跨语言 SDK 实现时按下表把内部错误归一到本节的错误码：

| 实现端 | 实现方式 |
|---|---|
| **Go** | `type ErrorCode string`，所有 error 类型实现 `Code() ErrorCode` 接口；上报 metrics 时 `metrics.OnError(topic, err)` 内部取 `err.Code()` 作为 label |
| **C++** | enum class `ErrorCode`；所有自定义异常带 `code()` getter |
| **Rust** | enum `Error { ... }`，每个 variant 对应一个错误码；`thiserror` 注 `#[error("...")]` 的 prefix 与本节一致 |
| **C#** | `enum AeronErrorCode`；所有自定义 exception 带 `ErrorCode` property |

**最低要求**：

1. 上报 metrics 时**必须**带 `error.code` 标签，值为本节表中的字符串
2. 日志格式建议带 `error.code` 前缀，便于 grep
3. 错误码新增需先在本节登记，跨语言端同步实施

**通用聚合 query 示例**（Prometheus）：

```promql
# 跨语言所有 consumer 的 frame 解码失败总数
sum by (error_code) (rate(aeron_consumer_errors_total{error_code=~"FRAME_.*"}[5m]))

# 跨语言所有 producer 的 backpressure 趋势
sum by (lang, error_code) (rate(aeron_producer_errors_total{error_code="PUBLICATION_BACKPRESSURED"}[1m]))
```

### 12.6 与现有 metrics 的关系

Java 端当前 metrics API（`ConsumerMetrics.onError(topic, partition, groupId, Throwable)` / `ProducerMetrics.onError(topic, partition, Throwable)`）已带 `partition` / `groupId` 维度，但仍未暴露显式 `error.code` 字段。**已知 TODO**：

- 后续可在 Java metrics 实现里通过 `ex.getClass().getSimpleName()` + message 前缀做归一，导出到 Micrometer 时打 `error.code` label
- 跨语言对端可以直接按本节规范实现，**不必等 Java 端 metrics 重构**

新建跨语言 SDK 时直接遵守本规范，Java 端 metrics 改造可作为后续优化项分批进行。

## 附：互通项目落地建议

如果你要从零起一个新语言的 SDK：

0. **30 分钟 Java↔X baseline**：先按本文档开头「快速开始」把 Java 端两进程 IPC echo 跑起来，**理解 driver / aeronDir / channel URI / streamId 的物理对齐**
1. **读完本文档 + [`aeron协议说明.md`](aeron协议说明.md)**
2. **先实现 §1 黄金 verify 路径的第 1 个测试**（IPC + RAW codec，单条 hello 消息），花一周做完即代表协议层互通通了
3. **每个 codec / compression 实现时**：拿 [`docs/wire-samples/*.hex`](wire-samples/) 做单元层级 bit-for-bit verify（不需要起 Aeron driver），是最高效的字节级 debug 手段
4. **再按业务最需要的 codec / compression 顺序补**（典型业务优先级：Protobuf > JSON > LZ4 > 其它）
5. **每加一个 codec / compression 都对应跑 §1 的对称双向测试**
6. **在自家 CI 里把 Java 参考实现作为对端跑互通测试**（CI 里跑 `gradle test` 拉起 Java consumer，新语言端跑 producer，反之亦然）
7. **最终发独立 repo**（如 `aeron-broadcast-go`），与 Java SDK 平级，共享 [`docs/aeron协议说明.md`](aeron协议说明.md) + 本文档作为契约
