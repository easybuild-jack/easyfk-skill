# 12 复核（子 agent 审代码）

写的人查自己，容易被自己的假设带偏：需求写了「失败要回滚」，代码里也写了回滚，但漏了某个分支，自己看十遍也看不出来。复核就是换一个没参与开发的人，只拿需求和设计去对代码。

## 1. 什么时候做

| 情况 | 复核 | 例子 |
|---|---|---|
| 新需求开发 | 做 | 新增业务功能、新主题的第一批改动 |
| 复杂变更 | 做 | 主流程变了、跨多个模块或层、动了对外契约（`IXxxApi`、`IXxxRemote`）、改了表结构、新增外部依赖 |
| 小改动 | 不做 | 修 bug、加或改一个字段、改默认值或配置、改日志和文案、调格式 |

判断不了时按大的算：复核半小时，漏一个分支上线排查半天。用户在任务里明确说不用复核的，照做，并在回复里记一句。

## 2. 审什么

按顺序过，前四项对不上就是阻断。

项目不是 easyfk 时，跳过第 3、4、5 项里依赖框架的部分（分层契约、框架规范项、组件选型），其余照审。

1. **需求覆盖**：需求文档里的目标、参与角色、输入输出、约束、不做什么，逐条找代码里的落点。缺一条、做偏一条都是阻断。
2. **设计对齐**：分析文档里的主路径、分支、失败处理、依赖的 easyfk 模块，代码里有没有对应；图里的每个判断点在代码里有对应分支；计划里的步骤都做了。
3. **分层与契约**：Controller 只依赖 `IXxxApi`；Service 不碰 Mapper 和 Entity；跨服务只用 `IXxxApi`；`IXxxApi` 加了方法时 `ApiServerImpl`、`ApiScImpl` / `ApiDubboImpl`、`IXxxRemote`、`RemoteImpl` 同步了（项目里有哪几种补哪几种）。
4. **规范项**：主键 `String` + UUID、`Dto` 上 `@PrimaryKey`、唯一字段 `@SingleUniqueField` 且有唯一索引、写多表带 `@Transactional(rollbackFor = Exception.class)`、业务异常走错误码枚举或 i18n。
5. **组件选型**：线程池、队列、缓存、锁、业务编号、序列化、JSON、Bean 拷贝、日期、加解密有没有自己造，而 easyfk 模块里已有。
6. **数据**：新增或改动的表和字段与分析文档一致；查得频繁的字段有索引；长度、精度、非空和默认值定得下；历史数据要不要刷。
7. **并发与性能**：热点、循环里查库或远程调用、全表查询、`queryList` 没有 `top`、锁和共享可变状态、热路径上频繁创建大对象。
8. **多写**：没要求的抽象、重复造的工具、能删的代码、需求范围外的功能。
9. **测试**：主路径、关键分支、失败路径有没有覆盖；没有测试的项目有没有说明怎么验证。
10. **文档影响**：业务数据依赖有没有变（新增外部数据来源、自管理数据增减、对外提供范围变了），变了要更新项目说明第 5 节。

## 3. 怎么起这个子 agent

要求三条：**独立**、**不带开发过程**、**只给材料**。

- 用 IDE 的 subagent / Task 工具起，或新开一个会话。不要在当前会话里让它「换个角度想想」，同一份上下文里的判断会互相污染。
- 不给它本次开发的对话、思考过程和自己的结论。给了它就会顺着你的说法找证据。
- 只给：仓库路径、需求、分析（含图）、计划、改动文件清单。

提示词模板，按实际情况换掉尖括号：

```text
你是本次改动之外的独立审查者，没参与开发，也不要看开发过程的对话记录。

仓库：<绝对路径>
需求：docs/requirement/<主题>-需求.md
设计：docs/design/<主题>-分析.md（同主题的流程图、时序图、架构图一并读）
计划：docs/plan/<主题>-计划.md
改动文件：
<git diff --stat 的输出，或文件清单>

按 easyfk-dev-skill 的 rules/12-review.md §2 逐项审。额外要求：
1. 需求每一条单独给结论：已实现 / 部分实现 / 未实现 / 实现与需求不符。
2. 设计里的分支和失败路径逐条核对，指出哪条没写。
3. 指出需求没要求、代码里多出来的东西。
4. 自己读代码确认，不猜；读不到的写「未找到」。

输出问题清单，按严重程度排序，每条给：【阻断】或【建议】、文件:行、问题、依据（需求第几条 / 设计哪一节 / 规范哪一条）、怎么改。没问题的项一句话带过。只指出问题，不重写代码。
```

## 4. 结果怎么处理

- **阻断级必须改**，改完让同一个子 agent 复审这一批问题，不复述其他内容。
- 最多两轮。两轮还有阻断，停下来告诉用户：卡在哪一条、试过什么、需要什么决定。不自己把它降级成「建议」。
- **建议级自己判断**：采纳的改掉；不采纳的在回复里说一句为什么，不要沉默略过。
- 子 agent 说「通过」也要看依据：有没有真的读到关键方法、需求是不是逐条核过。说得很笼统的，按没审算。
- 子 agent 判错的直接驳回并说明理由。最终判断权在自己，不在它。

## 5. 结果记在哪

回复里给一段复核结论：几轮、阻断几条已改、建议几条采纳几条、没采纳的原因。计划文档里同步更新状态和「复核」一行，格式见 [10-docs.md](10-docs.md) §3.1。不复述被改代码的细节。
