# 11 架构类项目

架构类项目是为业务开发服务、偏架构层的项目，不是普通的数据库应用：技术组件、SDK、starter、中间件、引擎、框架底层。开发内容不只是数据库增删改查，更多是线程、消息、状态、协议、自动装配和对外契约。

按交付形态分两种，一个项目可以两种都有：

| 形态 | 特征 | 例子 |
|---|---|---|
| 库形态 | 以 jar 发布，给其他项目依赖，本身不单独部署 | `lock-redisson`、`cache-caffeine`、`autoId-redis`、`etcd-cluster`、`easyfk-aeron`、业务方用的 SDK |
| 服务形态 | 独立部署的进程，以内存计算和消息为主 | 撮合、行情、风控、K 线、消息处理、数据代理、网关 |

本篇没有特别说明的条目两种形态都适用；标了「库形态」「服务形态」的只适用于那一种。

不属于这一类的：带数据库表和 Controller、以 jar 复用的业务模块（如 auth），结构见 [01-project.md](01-project.md) §2.4。架构类项目里的 CRUD 部分（如配置管理、流水查询）照普通业务项目的分层写（02 ~ 08）。

## 1. 开工方式

1. **先确认要不要做**：按 SKILL.md §1 查 easyfk-framework-skill，框架已有同类能力的，用现成的或在原组件上扩展，不另起一个。
2. **新项目**：模块由本 skill 设计，按 [10-docs.md](10-docs.md) §3 出需求、分析和计划，第一批主题固定叫「初版」。`初版-分析.md` 里定模块拆分（§3）、线程模型与状态（§5）、对外契约（§6 第 3 条）；`初版-架构图.md` 必有，并在 `docs/` 根目录写 `<项目名>项目说明.md`。文档没写完不建工程。
3. **已有项目**：先读根构建文件的模块列表、每个模块的依赖、自动配置类和配置属性类，再把本次要改的那条链路（入站 → 处理 → 出站，或入口类 → 内部实现）上的类读一遍，照现有的线程模型、包结构和注册方式改。不改模块结构，不换中间件；对外 API、配置项、消息契约、线程模型有变化的，属于重大调整，先出文档。

## 2. 组件选型

先按 SKILL.md §1 的三步查。架构类项目常用的能力对应的模块如下，类名和配置以对应版本的 `modules/xxx-skill.md` 为准：

| 需求 | 用这个 | 边界 |
|---|---|---|
| 进程间低时延广播（行情、成交回报） | `aeron-spring-boot-starter` + codec（`aeron-codec-fory` / `-sbe` / `-protobuf`） | 只做 fan-out，不持久化，不能承载必须送达的业务数据 |
| 多副本强一致状态（账本、订单簿） | `aeron-cluster-spring-boot-starter` / `aeron-cluster-client` | 状态机必须确定性：不做 IO、不读墙钟、不生成随机数 |
| 只有主节点执行，防旧主复活覆盖 | `etcd-cluster-spring-boot-starter` 选主 + Fence | 只放少量强一致状态；不用 redisson 锁代替选主 |
| 进程内生产消费 | `queue-disruptor`：消费者实现 `Processor<T>`，生产者用 `IngestQueueManager` | 内存队列，不保证不丢 |
| 需要持久化、ack、重投、回放的消息 | `mq-rocket` / `mq-kafka` / `mq-rabbit` | 消费端自己保证幂等 |
| 同机持久化顺序队列、堆外大容量 KV | `chronicle-queue` / `chronicle-map` | 只能单机，不能当跨机缓存或 MQ |
| 线程池、调度、重试 | `easyfk-thread` 的命名线程池或 `CustomTaskExecutor` | 不自己 `new ThreadPoolExecutor`；确实要自建线程时，线程名带项目或组件名 |
| 二进制序列化 | `serializer-fory` | — |

拿不准选哪个时，先看 easyfk-framework-skill §5.1 的易混场景。选型结果和理由写进 `分析.md`；准备新引入的，写明现有模块缺哪一项。

使用 Aeron、aeron-cluster、Chronicle 要加 `--add-opens` / `--add-exports` JVM 参数，清单见对应模块文档，写进启动脚本、测试配置和使用说明。

## 3. 模块拆分

从最少的模块开始，有理由才拆。

**服务形态**的起点：

- `xxx-common`：共用的模型、消息定义、常量和工具。
- `xxx-server`：可部署的进程，主逻辑在这里，按包分层。
- `xxx-api`：只有要给其他服务依赖的接口、消息模型或客户端时才建。

**库形态**的拆法：

| 情况 | 拆法 | 例子 |
|---|---|---|
| 只有一个实现 | 一个模块，接口、实现、自动配置都在里面 | `lock-redisson` |
| 一套接口有多个可替换的实现 | `<组件>-api` 放接口和模型，每个实现一个模块 | `autoId-api` + `autoId-redis` |
| 核心能力要能脱离 Spring 使用 | `-api`（接口）+ `-core`（实现，不依赖 Spring）+ `-spring-boot-starter`（自动配置和配置属性） | `etcd-cluster-api` / `-core` / `-spring-boot-starter` |
| 有多个可选扩展（codec、压缩、监控） | 每个扩展一个模块，使用方按需引入 | `aeron-codec-fory`、`aeron-compression-lz4` |

有下面的理由才多拆一个模块：

- 需要独立部署或独立扩缩容的进程（如网关进程和撮合进程分开）。
- 要给其他项目依赖、单独发布的契约、SDK 或可选扩展。
- 业务边界明显不同，而且变更和发布节奏不同。

不要这样拆：

- 按技术分层拆成 handler、service、dao 各一个模块。分层用包。
- 只有一个使用方的「公共」模块。
- 为「以后可能有别的实现」先拆 `-api`；为「以后可能用到」预留空模块，或只有一两个类的模块。

依赖单向，不循环：`xxx-common` 不依赖 `xxx-server`；实现模块依赖 `-api`，`-api` 不依赖实现；starter 依赖 core，core 不依赖 starter。同一领域的多个模块可以放在一个聚合目录下（如 `component-lock`），聚合目录只做归类，不放代码。拿不准要不要拆，先合在一起。

拆分结果写进 `docs/design/<主题>-架构图.md`：每个模块一句话职责，以及模块之间的依赖方向。

## 4. 包结构

**库形态**：包名以 `com.mcst.easyfk.<领域>.<实现>` 为根（独立工程用自己的根包，如 `com.mcst.cluster`），按职责分子包：

| 包 | 放什么 |
|---|---|
| 根包 | 对外的主入口（模板类、门面接口），如 `RLockTemplate` |
| `config` | `@AutoConfiguration` 自动配置类 |
| `properties` | 配置属性类 |
| `manager` / `support` | 内部实现，使用方不直接用 |
| `enums` | 枚举 |
| `exception` | 自己的异常类 |
| `spi` | 让使用方扩展的接口（有扩展点时才建） |

使用方只应该用到根包、`properties`、`enums`、`exception`、`spi` 里的类；`manager` / `support` 不对外承诺。

**服务形态**：`xxx-server` 里按链路环节分包，如入站（接收和解码）、核心处理、出站（发布和回报）、状态与恢复、配置。包名跟环节走，不照搬 controller / service / dao。

## 5. 线程模型与状态

架构类项目的正确性大多取决于「谁在哪个线程改哪份状态」。在 `分析.md` 里写清楚，代码照着写。库形态里没有自己的线程和状态的，跳过本节。

1. 每个环节跑在哪个线程或线程池上，环节之间用什么传递（disruptor、Aeron、MQ）。库形态写明对外方法是否线程安全、回调在哪个线程执行。
2. 核心状态（订单簿、账户、仓位、连接表）尽量只由一个线程修改，其他线程通过队列把事件交给它。确实要多线程共享时，写明用什么同步手段，以及为什么不能单线程。
3. 热路径线程上不做阻塞操作：不查库、不调远程、不等锁、不同步写文件。这些放到旁路线程或异步链路上，并写明结果回来怎么处理。
4. 每一份状态写明存在哪儿、进程重启后怎么恢复（aeron-cluster 快照与日志回放、chronicle 文件、从上游重放），以及恢复期间是否对外服务。
5. 有主备或多副本时，写明谁可以写、切主时旧主怎么停写（etcd Fence 或 aeron-cluster 的角色）。
6. 自己创建的线程、连接、文件句柄要有关闭路径：先停接收，再处理完在途任务，最后释放资源。库形态在 Bean 销毁时关闭（`destroyMethod` 或 `DisposableBean`）。

## 6. 写代码

通用写法（最少实现、先检查后主流程、中文日志和注释）照 SKILL.md §5。另外注意：

1. **热路径**：每条消息、每次调用都要走的代码。
   - 循环里不做远程调用、查库和不必要的分配；不用异常控制流程。
   - GC 看热路径上是否频繁创建短命对象，或把大集合长时间留住（如只增不删的 Map）。
   - 能指出具体热点就改；说不出热点，不为性能加缓存、对象池或异步。做了对象复用的，写一行注释说明复用范围和线程约束。
2. **确定性**：aeron-cluster 状态机里不读 `System.currentTimeMillis()`、不用随机数、不做 IO、不依赖 `HashMap` 遍历顺序；时间和随机值由输入消息带进来。
3. **对外契约**：对外接口、模型、异常、配置项、消息格式都是契约，改动前查清楚谁在用。
   - 消息字段只增不改，已发布的字段不改类型、不复用编号（SBE、Protobuf）。
   - 接口删除或改签名前先标 `@Deprecated` 并给出替代方法，至少保留一个版本。
   - 配置项不随意改名、改含义、改默认值；确实要改时保留旧名兼容一个版本或启动时明确提示。
   - 契约改动属于重大调整，在分析里写明兼容方式和上下游的发布顺序，并在使用说明和 easyfk 对应版本的 `VERSION.md` 里写明（框架自身的项目）。
4. **失败处理**：解码失败、校验不通过、下游不可用时怎么办（丢弃并计数、进死信、拒绝并回报、抛异常），每一种写清楚，不静默吞掉。库形态用 `exception` 包里自己的异常类，信息写清原因和相关的配置项或参数，不依赖业务项目的错误码枚举。
5. **日志**：热路径上不逐条打 INFO；异常和状态变化（启动、切主、恢复完成、背压丢帧、连接断开）必须打，写清对象和结果。逐条排查用 DEBUG 或计数指标。不打印密码、密钥、Token。
6. **配置**：配置属性类前缀 `easyfk.config.<领域>[.<实现>]`，写法见 [09-config.md](09-config.md) §2。通道地址、streamId、线程数、队列长度这类部署时会变的做成配置，算法常量不做成配置。每个字段写中文注释，说明作用、单位和默认值；必填项启动时校验，缺了直接失败并说清楚是哪一项。

## 7. 自动配置（库形态）

靠 Spring Boot 自动配置装配，不靠组件扫描（使用方的启动类包路径和组件不同）。在 [09-config.md](09-config.md) §1.1 的基础上：

1. 类上不加 `@Component`、`@Service`；全部在 `config` 包的 `@AutoConfiguration` 配置类里用 `@Bean` 注册，配置类写进 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。
2. 每个 `@Bean` 加 `@ConditionalOnMissingBean`，返回类型写接口，让使用方能用自己的实现覆盖。
3. 依赖可选类库的 Bean 用 `@ConditionalOnClass` 保护，避免使用方没引那个库时启动失败。
4. 引入后会连接外部资源、启动线程或改变全局行为的，用 `@ConditionalOnProperty` 加开关，默认值在分析里定；引入即生效的，在使用说明里写明。
5. 有顺序要求时用 `@AutoConfiguration(after = ...)` 声明，不靠类名排序。

## 8. 依赖

1. `easyfk-dependencies` 已经管理的依赖（easyfk 模块和 BOM 里的第三方库）不写版本号。
2. BOM 里没有的依赖自己写版本，在根构建文件里集中锁定（Gradle 用版本目录 `libs.versions.toml` 或根 `build.gradle` 的统一变量，Maven 用根 `pom.xml` 的 `dependencyManagement`），不散落在各子模块。新引入前先在回复里说明理由。
3. 使用方一定会自己带的库（Spring Boot、spring-web、openfeign、dubbo 等）用 `compileOnly`；对外接口的参数或返回值里出现的类型所在的库用 `api`；其余用 `implementation`。
4. 不引入 easyfk-framework-skill §6 列为不要引入的库，不引入和已有库功能重复的库。

## 9. 文档

要给别人接入的（库形态、对外提供接口或 SDK 的服务）必须写使用说明文档，放 `docs/guides/<项目名>-<组件或功能名>使用说明文档.md`，写给接入方，内容以代码为准：

1. 适用场景和不适用的场景（能力边界）。
2. 怎么引入：依赖坐标（BOM 已管理的不写版本）、要配合引入的其他模块、需要的 JVM 参数。
3. 每个配置项：作用、类型、默认值、是否必填。
4. 各环境的完整示例配置。
5. 代码用法：主入口类的典型调用，以及怎么用自己的实现覆盖默认 Bean。
6. 上线检查和常见问题：常见报错文本和原因。

框架自身的组件新增、移除或改动了对外 API、配置项时，同步改使用说明，并提醒用户同步 easyfk-framework-skill 对应版本的 `modules/xxx-skill.md`，以及 easyfk-framework-skill §4、§5 的能力清单。

## 10. 测试

用项目已有的测试方式，覆盖：

- 主路径：一条消息从入站到出站，或一次调用从入口到结果，结果正确。
- 关键分支和失败路径：校验不通过、下游不可用、重复消息。
- 有并发场景的（锁、队列、缓存、共享状态）覆盖并发下的正确性。
- 状态恢复：有快照或回放时，重启后状态和重启前一致。aeron-cluster 状态机用同一串输入跑两遍，状态一致。
- 库形态：默认装配能工作；使用方自定义同类型 Bean 时默认 Bean 不再创建；关闭开关后不装配；关闭容器后线程、连接都已释放。

单纯的 getter、名字已经说明行为的简单方法不必单写测试。压测不是每次都要做，改了热路径或线程模型时，在回复里说明要不要压、压什么。

## 11. 自检补充

SKILL.md §6 之外再查：

1. 线程归属、状态存放和恢复方式，和 `分析.md` 一致。
2. 热路径上没有阻塞 IO、远程调用、锁等待，没有循环里的大量分配。
3. 不持久化的通道（aeron、disruptor）没有承载必须送达的业务数据；aeron-cluster 状态机没有墙钟、随机数和 IO。
4. 对外 API、配置项、消息契约的改动是兼容的，或已标 `@Deprecated`、写进使用说明和发布顺序。
5. 库形态：没有 `@Component` / `@Service` 等扫描注解，新配置类已写进 `AutoConfiguration.imports`，`@Bean` 都有 `@ConditionalOnMissingBean`，可选依赖有 `@ConditionalOnClass`。
6. BOM 已管理的依赖没写版本，BOM 没有的版本集中锁定在根构建文件；`compileOnly` / `api` / `implementation` 用得对。
7. 线程、连接有关闭路径；使用说明文档和代码一致。
