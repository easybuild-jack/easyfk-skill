# 10 文档、画图与迭代记录

## 1. 文档要不要写

先判断这次改动属于哪一类，再决定出不出文档。

| 类型 | 例子 | 文档 |
|---|---|---|
| 小改动 | 加或改一个字段、加一个判断、改默认值或配置、修 bug、改日志和文案 | 不新建文档，不记迭代记录。已有设计文档恰好写到这处行为、改完会失真时，只改那一处 |
| 重大调整 | 新业务功能、主流程变了、业务规则或对接的系统变了、模块或部署边界变了、新建项目 | 按 §4 出文档，并记迭代记录 |

判断不了时，开工前先问用户这次要不要出文档，说明你倾向哪一类、依据是什么。用户明确说不要文档时，照做，并在回复里记一句跳过了文档。

## 2. 文档目录

以项目 `trade-server`、主题「订单撤销」为例：

```
trade-server/                    项目根
├── README.md                    概览大纲：一句话定位、功能大纲、快速开始、文档索引，见 §5.3
└── docs/
    ├── trade-server迭代记录.md  项目级：按时间倒序记业务需求的立项、变更和里程碑，见 §7
    ├── trade-server项目说明.md  项目级：背景、需求、功能、模块划分、业务数据依赖，见 §5
    ├── requirement/             需求
    │   └── 订单撤销-需求.md
    ├── design/                  设计：分析和所有的图
    │   ├── 订单撤销-分析.md
    │   ├── 订单撤销-流程图.md   按需，见 §6
    │   ├── 订单撤销-时序图.md   按需
    │   ├── 订单撤销-时序图-<环节>.md  拆出去的细节，<环节>与主体图里的名字一致
    │   ├── 订单撤销-架构图.md   按需；新项目必有，写模块拆分
    │   └── 订单撤销-架构图-<环节>.md
    ├── plan/                    计划
    │   └── 订单撤销-计划.md
    ├── guides/                  按需：只在需要输出使用说明文档时才建
    │   └── <项目名>-<组件或功能名>使用说明文档.md
    └── reverse/                 easyfk-reverse-skill 的反推报告，不放设计文档；项目没有项目说明时，业务数据依赖清单也在这里
```

- **固定目录**：`requirement`、`design`、`plan` 三个目录名固定，不按主题再建子目录。分析、流程图、时序图、架构图都属于设计，全部放 `design`。
- **主题名**：中文业务名，不超过 10 个字，如「订单撤销」「统一机密管理」。不带日期、序号、空格和标点。新项目第一批需求的主题固定叫「初版」；之后按业务名起主题。
- **主题文档**：文件名 `<主题名>-<文档名>.md`，不加项目名、版本号或日期。同一主题在三个目录里用同一个主题名。没有的文档就不建，不建空文件。
- **根目录的 README**：`README.md` 放项目根目录，是项目的概览页，只写结论和索引，细节一律放 `docs/`，见 §5.3。文件名固定，一个项目只有一份。
- **`docs/` 根目录的两份文档**：固定是 `<项目名>迭代记录.md` 和 `<项目名>项目说明.md`，项目名和后面的文字之间不加连字符。`docs/` 根目录不放其他文档。
- **项目名**：Gradle 用 `settings.gradle` 的 `rootProject.name`，Maven 用根 `pom.xml` 的 `artifactId`；都没有时用仓库根目录名。使用说明文档也以 `<项目名>-` 开头。
- 已有文档不符合上面结构的，改到这个主题时按上面的结构挪过去并改名，同时把所有引用一起改掉，不另建一份。没改到的主题不单独迁移。
- 使用说明文档只在项目要给别人接入时才写（组件、SDK、对外服务），或用户明确要求时。架构类项目要给别人接入的必须写，内容要求见 [11-architecture.md](11-architecture.md) §9。写给接入方：怎么引入、每个配置项、各环境的完整示例配置、代码用法、上线检查和常见问题。配置项、默认值、报错文本都以代码为准。
- 项目已有其他文档目录时，本主题的文档仍按上面的结构放，在回复里说明；不移动与本次无关的旧文档。
- 文档之间用相对路径链接。目录或文件改名后，把所有引用一起改掉。

## 3. 重大调整开工前

属于重大调整时，没有需求、分析和计划，不写业务代码。按顺序做，前一步没写完不进入下一步：

1. **定主题，整理需求**，写 `requirement/<主题>-需求.md`：目标、参与角色、输入输出、约束、不做什么。不把闲聊扩写成需求。同时在迭代记录最上面记一条立项。
2. **分析需求**，写 `design/<主题>-分析.md`：主路径、分支、失败怎么处理、依赖哪些 easyfk 能力。按 SKILL.md §1 标出要用的模块；准备新引入的，写明现有模块哪一项满足不了。涉及数据库的，列出新增或改动的表和字段。新项目在这里定模块拆分；架构类项目见 [11-architecture.md](11-architecture.md) §3，并写清线程模型与状态（§5）和对外契约（§6）。最后写一节「图」：这次画哪几张、各自为什么要画，不画的为什么不需要，各一句话。
3. **画图**：只画上一步判断需要的，放 `design/`，见 §6。
4. **计划**，写 `plan/<主题>-计划.md`：按步骤列出改哪些模块和层、先读 easyfk-framework-skill 的哪一篇、怎么验证。不写框架里已有能力的实现细节。开发步骤的完成情况在这里勾选，不写进迭代记录。文档结构和状态值见 §3.1。
5. **新项目从零开始时**，写项目说明（见 §5），再按它写根目录的 `README.md`：只写结论和索引，不重复项目说明的正文（见 §5.3）。

图和计划描述的是本次要做的行为。手册或示例里的业务数据只作举例，不当成必须实现的数据。

### 3.1 计划文档

每一步任务的进展都落在计划文档里。上层总管的角色按这份文档看进度、判断任务停在哪，不看聊天记录，所以状态必须及时改、值必须统一。

```markdown
# 订单撤销 计划

> **状态**：待复核
> **最后更新**：2026-11-18
> **复核**：第 1 轮，2 条阻断待改

1. [x] 读 easyfk-framework-skill §5 做组件选型，确认用 easyfk-cache
2. [x] `order` 模块加 `CancelReq`、`CancelResp`
3. [x] `IXxxApi#cancel` 与 `ApiServerImpl`、`IXxxRemote`、`RemoteImpl` 同步
4. [ ] 补失败路径测试，覆盖库存不足
```

- **状态**只能取五值之一，不自造：`未开始`、`进行中`、`待复核`、`已完成`、`已阻塞（写明原因）`。步骤都做完但复核没过是 `待复核`；复核通过、测试过、该更新的文档也更新完，才是 `已完成`。
- **最后更新**写日期，每次动这个文件都改，停滞一眼看得出。
- **复核**写 `未做`、`第 N 轮通过`、`第 N 轮，几条阻断待改` 或 `不适用（小改动）`。要不要复核见 [12-review.md](12-review.md) §1。
- 步骤用 `- [ ]` / `- [x]` 勾，勾上才算做完；做了一半的保持 `[ ]`，在步骤后面补一句到哪了、卡在哪。
- **什么时候更新**：开工时把 `未开始` 改成 `进行中`；每完成一步勾一步；开发做完进复核时改成 `待复核`；复核和测试都过、文档也改完，改成 `已完成`。不等用户催，也不留到最后一次性补。
- 计划里步骤有增减、顺序变了，同步改这份文档，同时核对分析文档要不要跟着改。计划和代码对不上时以分析文档为准，改计划或改代码，不两边各说各的。
- 小改动不建计划文档，也就不涉及状态更新；它在回复里说明完成情况即可。已有项目上的一次改动没走文档流程、因而没有计划文档的，同样在回复里说明，不为了更新状态硬建一份计划。

## 4. 写完和设计对齐

自检时（SKILL.md §6）对照本主题的需求、分析、计划和图：主路径、分支、失败处理是否一致。对不上就改代码，或改设计文档；改的是业务需求时，在迭代记录里记一条需求变更。改动来自反推，或改动的模块在 `docs/reverse/` 里已有报告时，同时改 `<项目名>-业务分析报告.md`、`<项目名>-架构分析报告.md` 里对不上的小节；该模块已拆出去时，连同 `docs/reverse/<模块>/` 下对应的文件一起改。报告的结构见 easyfk-reverse-skill。

改动让业务数据依赖变了（新增或去掉外部数据来源、自管理数据增减、对外提供的数据范围变了），同步改 `<项目名>项目说明.md` 的「业务数据依赖」一节，落地顺序见 §5.2。

## 5. 项目说明与 README

根目录的 `README.md` 是项目的概览（见 §5.3），`docs/<项目名>项目说明.md` 是正文。README 只给结论和索引，详细内容写在项目说明里，不重复叙述；两边说的不一致时以代码为准，两份一起改。

`docs/<项目名>项目说明.md` 写给第一次接触项目的人，要答清三件事：这是什么项目、负责什么、碰了哪些业务数据。这三样是上层分派任务的原始事实，项目如实登记即可，不替上层判断某次变更涉及哪些项目。正文之前先写一块**项目定位**（§5.1），正文固定五节，顺序不变：

1. **背景**：为什么要做，要解决什么业务问题。
2. **需求**：目标、参与角色、范围，以及明确不做什么。
3. **功能**：对外提供哪些功能，每项一两句话。
4. **模块设计及划分**：有哪些模块，每个模块的职责、依赖方向，以及为什么这样拆。有架构图时放主体架构图或链接过去。
5. **业务数据依赖**：本项目依赖哪些外部业务数据、自己管理哪些、对外提供哪些，见 §5.2。

新项目从零开始时写全项目定位和五节，内容来自本项目的需求、设计和计划。细节不重复，链接到 `requirement/`、`design/`。之后的重大调整改了功能范围或模块划分时同步改。

已有项目默认不写，用户明确要求时才写，内容以设计文档和代码为准；但**两处例外**——项目定位（§5.1）和业务数据依赖（§5.2）按各自「什么时候改」的要求维护，只要触发了就要落到项目说明里。项目还没有项目说明时，按 §5.2 的落地顺序处理：优先写进已有的业务数据依赖文档，两者都没有才新建，新建时只填得来内容，不为了凑结构编背景和需求。

定位块跟着文档走：落在项目说明里就是它的开头，落在独立的业务数据依赖文档里就放那份的标题下，不为了放定位专门新建一份项目说明。

### 5.1 项目定位

写在项目说明标题下的第一段，用一块引用说清这个项目属于哪一类、负责什么。这一块只登记事实，供上层汇总和分派任务时用。

```markdown
> **项目类型**：业务项目 / 组件项目
> **业务域或服务对象**：...
> **一句话本职**：...
```

- **业务项目**：直接实现业务规则、对外提供业务功能，业务方会直接对它提需求。「业务域或服务对象」填它覆盖的业务，如「用户与权限」「订单与支付」「风控」。
- **组件项目**：本身不含业务规则，为业务项目提供通用能力、数据流转或基础设施，包含组件、SDK、starter、中间件、引擎、数据代理、集群和存储封装，如 data-agent、aeron-cluster、mq-kafka、db-redis。「业务域或服务对象」填它服务于谁、承载什么，如「为交易和风控提供实时行情分发」「全系统共用的消息通道」。

**怎么判断**（写文档时定一次，之后只在项目性质变化时才改，跟具体需求无关），按顺序，命中即定：

1. 业务方提需求时会不会点名这个项目？会 → 业务项目。
2. 代码里有没有业务规则判断（状态机、额度、费率、审批、风控规则、业务校验）？有 → 业务项目；只有协议、路由、编解码、存储、调度、连接管理 → 组件项目。
3. 换一个业务域还要不要它？换掉业务、它照样留着且代码基本不动 → 组件项目。

一个工程里两种都有（例如业务工程里带的公共 starter）时，按主形态写，并在「一句话本职」里说明哪一部分不对业务负责。

**组件项目必须写清服务对象**，否则上层分派任务时判断不了哪些需求会经过它：服务于哪些业务项目、在这条链路的哪个位置、承载哪类数据。只写「服务于业务」等于没写。

**和任务分派的关系**：「一次需求变更涉及哪些项目」由上层总管的 skill 判断并分发（该 skill 不在本套件内，本套件也不去模拟它），各项目不做这个全局判断，也不自行去猜跟自己有没有关系。本项目收到分派的任务后自己核三件事——是不是我的职责、这个改动要不要做、要改哪些地方；判定不属于自己时把理由说清退回，不硬接。定位块和业务数据依赖表就是给这个判断用的原始事实。

**和开发规范的对应**：业务项目对应 SKILL.md 第 0 节的「普通业务项目」（按分层写 CRUD 业务），组件项目对应「架构类项目」（组件、SDK、starter、中间件、引擎，按 [11-architecture.md](11-architecture.md) 写）。项目说明只写定位这一句，开工方式仍按 SKILL.md 第 0 节判断。

**什么时候改**：项目性质变了才改——业务逻辑被抽走做成通用组件（业务项目 → 组件项目），或组件里长出了业务规则（反过来）。平时不动。

### 5.2 业务数据依赖

这一节登记本项目碰了哪些业务数据：依赖哪些外部数据、自己管理哪些、对外提供哪些，各自从哪来、谁在用。「变更影响」一列写的是这份数据本身变了会波及本项目的哪些地方，属于静态事实，不针对某一次具体需求——某次变更实际涉及哪些项目由上层分派，本项目收到任务后照这一列核自己的改动范围。它写在项目说明里，是因为这份数据的变化往往横跨多个模块：依赖了行情数据，行情的字段或口径一变，所有拿它计算的地方都要动，只在代码里搜很难看全。

**什么算业务数据**：业务方一句话能说清的数据集合，如行情数据、仓位数据、账户数据、订单数据、持仓数据、商品数据、用户数据、字典数据。**不算**中间件实例、连接池、日志、监控指标、纯技术配置。

按业务语义归并，不按存储方式拆：一个业务数据可以落在多张表、多个 topic、多个接口上，合成一行；一张表也可能只是某个业务数据的一部分，不单独占一行。命名用业务方的说法，不用表名或类名。

**表格**：

| 业务数据 | 说明 | 关系 | 来源 / 存储 | 代码位置 | 使用方 | 变更影响 |
|---|---|---|---|---|---|---|

- **关系**：`依赖`（只读，外部或别的系统提供）、`管理`（本项目产生并维护）、`对外提供`（本项目产出、别人消费）。既自管理又对外提供时写「管理，对外提供」。
- **来源 / 存储**：表名（Entity 的 `@TableName`）、Redis key 前缀、MQ topic 与消费组、RPC 契约 `IXxxRemote`、Aeron topic、外部 HTTP 接口、配置文件、本地文件，多个用顿号隔开。
- **代码位置**：`包.类#方法`，或模块 / 层，以能指回代码为准。
- **使用方**：本项目里用到它的模块、接口、定时任务、消费端。
- **变更影响**：上游定义或口径变了（加字段、改单位、改更新频率、换数据源、停止提供）时，本项目要动的地方。写到模块、接口或 `类#方法`，只能定到环节的写环节；不写「可能受影响」。

表格之后按数据各写一条「什么变了 → 要动哪里」，点名最容易漏的联动，如「行情数据的合约乘数变了 → 保证金计算（`XxxService#calcMargin`）、涨跌停校验」。

定位是组件项目的（§5.1）通常没有自管理数据，写清它承载、转发、缓存了哪几类业务数据、服务于谁即可；完全不碰业务数据的，写一句「本项目不处理业务数据」并说明它在链路上承载什么，表格留空，不编。

**什么时候维护**：

- 新项目：随项目说明一起写，从需求、设计和代码里取。
- 重大调整：新增或去掉外部数据来源、自管理数据增减、对外提供的数据范围变了，同步改这一节。
- 小改动不单独改；但它让表格失真的（多了一个数据来源、换了一个字段口径、换了一个调用方），顺手改那一行。
- 拿不准的（配置里有、代码里找不到读取方；命名像业务数据但没人用）不写进表格，放在这一节末尾的「未证实」。

**落在哪**（按顺序找第一个存在的，改它，不新建第二份）：

1. `docs/<项目名>项目说明.md` 存在 → 改它的第 5 节；顶部还没有定位块时，按 §5.1 判断后一并补上。
2. 不存在，但 `docs/reverse/<项目名>-业务数据依赖.md` 存在（反推时生成的）→ 改那一份，标题和表格结构与本节一致，定位块放它的标题下。
3. 都不存在 → 新建 `docs/<项目名>项目说明.md`，先写定位块（§5.1）和第 5 节，其余四节按已知信息补，缺的标「待补」。已有项目不必为了凑齐结构去编背景和需求。

### 5.3 README

`README.md` 固定在项目根目录，是别人打开仓库先看到的那一页：只做概览和索引，让人快速知道这是什么项目、能干什么、怎么跑起来、详细内容去哪看。同一项目只有一份，文件名固定 `README.md`。

**固定五块，顺序不变**：

1. **一句话定位**：是什么项目、解决什么业务问题，两三句话，和项目说明的定位块（§5.1）一致。
2. **功能或模块大纲**：只列名字加一句话，不展开职责边界和依赖方向。
3. **技术栈与环境**：主要框架、JDK 版本、依赖的中间件、私服配置的入口。
4. **快速开始**：构建、改哪个配置、启动命令，跑起来绕不开的步骤。
5. **文档索引**：链接到 `docs/<项目名>项目说明.md`、`requirement/`、`design/`、`plan/` 下与该阶段相关的文档，有使用说明时一并给出。

样例（内容随项目换，结构和篇幅按这个来）：

````markdown
# trade-server

交易下单服务，负责订单的创建、修改、撤销和状态流转，供客户端和管理后台调用。

## 功能

- **订单管理**：下单、改单、撤单、查询。
- **风控校验**：下单前校验额度、频率和价格笼子。

## 技术栈

Java 17、Spring Boot 3、easyfk 3.5.16、MySQL 8、Redis 7。私服配置见 <https://www.easybuild.pro/easyfk>。

## 快速开始

```bash
./gradlew :trade-server-web:bootRun
```

开发配置改 `trade-server-web/src/main/resources/application-dev.yml`。

## 文档

- [项目说明](docs/trade-server项目说明.md)：背景、需求、功能、模块划分、业务数据依赖
- [需求](docs/requirement/) · [设计](docs/design/) · [计划](docs/plan/)
````

**不写的**：详细的业务规则和流程、字段与表结构、模块内部设计、接口和参数清单、配置项逐条说明、迭代历史、部署运维细节。这些属于项目说明和 `docs/` 下的需求、设计文档，README 里一句结论加一个链接即可，不复制过来。

**篇幅**：整份控制在一屏到两屏（50 行以内）看得完。超过这个长度说明细节没下沉，挪进项目说明。

**什么时候写、什么时候改**：

- 新项目从零开始时随项目说明一起写，先有项目说明再写 README。
- 已有项目没有 README 的，用户要求时或本次动到项目说明时补一份，内容从代码和现有文档取，不编造。
- 重大调整改了项目定位、功能范围、模块划分、技术栈或启动方式的，同步改对应的一两行；只改实现细节、字段、配置值的不动 README。
- 小改动不碰 README；但它让 README 里某一句话失真的（变了启动命令、多了一个模块），顺手改那一句。

## 6. 画图

不是每个需求都要画图：

| 图 | 什么时候画 | 什么时候不画 |
|---|---|---|
| 流程图 | 有多个步骤，且有分支、失败出口或状态流转 | 步骤是一条直线，三五句话说得清，如加一个查询接口 |
| 时序图 | 多个角色、跨进程或跨系统调用，或有异步、回调、重试 | 只在一个进程里同步调用 |
| 架构图 | 新建项目，或进程、模块、部署边界、对外依赖有变化 | 只在已有模块里加逻辑，结构不变 |

都不需要时，在 `分析.md` 的「图」一节写明原因。拿不准就不画，先用文字写，评审看不懂再补。

用标准 Mermaid 语法，写在 Markdown 的 `mermaid` 代码块里，进版本库：

- 流程图 `flowchart`；时序图 `sequenceDiagram`；架构图 `flowchart`，进程或部署单元用 `subgraph` 框起来。
- 时序图和架构图先给一张主体图，只保留参与者和主路径。分支、失败、重试、配置开关放到细节图 `时序图-<环节>.md`、`架构图-<环节>.md`，每张图只讲一件事。细节文件第一行写明对应哪份文档的哪一节；主体图里留链接。

常见渲染失败的写法：

- 节点 ID 用英文字母和数字，显示文字可以是中文：`A["下单校验"]`。
- 文字里有空格、括号、冒号、竖线等符号时，用双引号包起来。
- 换行用 `<br/>`，不写 `\n`。
- 节点文字不要是全小写的 `end`。
- 一个代码块只放一张图。

图要在预览里不放大也看得清：

- 默认 `flowchart TB`，不把十几个节点排成一行 `LR`。
- 主体架构图每个进程或部署区只画一个节点，节点总数控制在 10 个左右。
- 连线文字只写协议或动作（`Feign`、`Dubbo`、`写入`），端口等细节写在图下面的表格里。
- 字小到要放大才能看清时，拆图，不靠缩放。

## 7. 迭代记录

`docs/<项目名>迭代记录.md` 是整个项目的业务迭代记录，一个项目只有一份。给负责人和业务方看，用业务语言写，不写开发过程和技术细节。小改动不记。

只记这几类事件：

- 立项或提出新需求：要解决什么业务问题。
- 需求变更：范围、业务规则、对接的系统或环境变了，写改成什么、为什么。
- 里程碑：完成开发、上线、灰度、暂停、取消。
- 还没做完的业务事项，写「待xx」。

不写：开发步骤、测试数、依赖选型、类名、修了什么 bug。

一律倒序：

- 按主题分节，节标题是主题名，括号里写这个主题最近一条记录的日期。
- 节按最近一条记录的日期倒序排。某个主题新记了一条，就把这一节移到最上面，并更新标题里的日期。
- 节内一行一件事，按日期倒序。「待xx」放在节内第一行。
- 每节第一行是链接，指向该主题的需求文档。

```markdown
# 迭代记录

## 订单撤销（2026年11月12日）

需求文档：[订单撤销](requirement/订单撤销-需求.md)

- 待开发：撤销后通知风控。
- 2026年11月12日，立项：用户下单后 30 秒内可以自助撤销，减少客服人工处理。

## 统一机密管理（2026年11月10日）

需求文档：[统一机密管理](requirement/统一机密管理-需求.md)

- 待上线：在一个节点灰度验证。
- 2026年11月10日，完成整体项目开发。
- 2026年11月6日，需求变更：改为接入现有的 easyfk 业务系统。
- 2026年11月3日，立项：交易系统多地部署，需要统一管理数据库密码、API Key 等凭据，凭据不落代码和日志。
```

需求变更时，同步改掉需求、分析、图和计划里失真的地方。
