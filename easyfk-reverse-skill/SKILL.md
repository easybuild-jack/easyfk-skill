# EasyFK 从代码反推业务与架构

这个 skill 只做理解：从现有代码反推高可用方案、业务流程和系统架构，写成报告。**只读代码和文档，不编译、不运行、不改业务代码，不补功能。** 反推完要接着改代码时，按 easyfk-dev-skill 做。

每次产出两份报告、一份清单：

- **业务分析报告**，放 `docs/reverse/`：写流程。
- **架构分析报告**，放 `docs/reverse/`：写结构。
- **业务数据依赖**：这个项目依赖、自管理、对外提供了哪些业务数据（§7.3）。项目里已有 `docs/<项目名>项目说明.md` 时，写进它的「业务数据依赖」一节；没有时单独出一份 `docs/reverse/<项目名>-业务数据依赖.md`。

两份报告都先总体、再细节，模块名一致。只有细节、没有总体，这份反推不算完成。业务数据依赖最容易被漏掉，但它决定的正是「业务或需求变了，这个项目要不要动、动哪里」，所以和另两份一起交付，不当作可选项。

代码是当前行为的依据。注释、设计文档和代码不一致时，写代码实际在做什么，并在「与文档的差异」里单列。不把猜到的规则写成已经实现的流程。

## 0. 先做四件事

0. **确认是 easyfk 项目**：从项目本身判断，构建文件引入了 `easyfk-` 开头的组件坐标（如 `easyfk-dependencies`），或源码包名以 `com.mcst` 开头，就使用本 skill；识别不到就不使用。细则同 easyfk-dev-skill 的「项目识别」。
1. **确认套件已安装**。本 skill 属于 easyfk-skill 套件，要用到另外两个 skill：
   - easyfk-framework-skill：识别框架调用是什么。
   - easyfk-dev-skill：项目类型、文档目录、项目名取法和画图规范。

   查找和安装方法见 easyfk-dev-skill 的「套件安装检查」一节；easyfk-dev-skill 本身也没装时，按下面的方式安装整个套件（三个 skill 一起装到本 skill 所在的 skills 目录，安装前在回复里说一句装到哪里）：

   ```
   git clone --depth 1 https://github.com/easybuild-jack/easyfk-skill.git <临时目录>/easyfk-skill
   powershell -ExecutionPolicy Bypass -File <临时目录>/easyfk-skill/install.ps1 -Target <skills 目录>   # Windows
   sh <临时目录>/easyfk-skill/install.sh <skills 目录>                                              # macOS / Linux
   ```

   没有 git、网络不通或安装失败时，停下来告诉用户，不凭记忆解释框架调用。下文的 `<framework>` 指找到的 easyfk-framework-skill 目录。
2. **确定 easyfk 版本**：按 easyfk-framework-skill 的 §0.1 找到项目的 easyfk 版本，到 `<framework>/versions/index.md` 定位快照。下文的 `modules/xxx-skill.md` 都指 `<framework>/versions/<版本>/modules/` 下的文件。
3. **认项目类型**：按 easyfk-dev-skill 第 0 节和 `rules/01-project.md` §2 判断。类型决定反推的侧重点：

| 类型 | 侧重 |
|---|---|
| 普通业务项目（single / sc / smart / 组件化） | 业务规则、接口与权限、数据隔离、跨服务调用；标准 CRUD 归并（§4 第 2 条） |
| 架构类项目·服务形态（撮合、行情、网关等） | 线程模型、消息链路、状态与恢复、选主和分片 |
| 架构类项目·库形态（组件、SDK、starter） | 对外入口类、自动装配、配置项、扩展点；高可用写它运行在哪个宿主里 |

## 1. 报告里的「模块」怎么定

报告里的模块是**业务模块或部署单元**，不是 Gradle / Maven 的构建模块。

- 普通业务项目：`-api`、`-server`、`-prd-bms`、`-prd-client`、`-sc-client`、`-sc-provider`、`-orm-api`、`-orm-plus` 这些是同一个业务的不同分层，合成一个报告模块，按业务域命名（如「订单」「权限」）。一个构建模块里有多个业务域时（如单模块项目），按业务域拆成多个报告模块。
- 架构类项目：服务形态按进程（部署单元）划分；库形态按对外提供的能力划分，`-api` / `-core` / `-spring-boot-starter` 合成一个。
- 在业务报告的「模块」一节放一张对照表：报告模块 → 包含的构建模块 → 是否独立部署。两份报告都用这张表里的模块名。

## 2. 顺序

先总体，再每个模块的细节；每个模块先写高可用，再写业务流程。总体没写完，不写模块内部的图。

1. 读项目已有的代码和文档：根构建文件的模块列表和每个模块的依赖、启动类、`AutoConfiguration.imports`、`application*.yml`，以及仓库里已有的说明（`docs/`、README）。按 §3 找出所有入口，同时看选主、成员、分片、锁和集群配置。文档和代码不一致时以代码为准，差异记下来。
2. 写总体：项目做什么、不做什么；按 §1 定模块并写清每个模块的作用；模块之间的调用链和一条总体业务流程。调用链按代码里的真实调用归并，不按目录名猜。
3. 逐个模块写细节，顺序和总体里的模块清单一致：先高可用，再入口、业务描述和图。不要把整个仓库的内部分支画进总体那张图。
4. 模块追完后写业务数据依赖（§7.3）。原料在追的过程中已经记下（§4 第 7 条），这时按业务数据归并成表，补「变更影响」和「变更关注点」，再按 §7.3 的规则决定写到项目说明还是单独成文。

用户点名只追一个模块时，总体仍先写这个模块在整条流程里的位置和上下游，再写它的高可用和业务流程。

## 3. 找入口

easyfk 项目的入口按下表识别。注解和基类以 `modules/xxx-skill.md` 为准，表里只是常见写法：

| 入口 | 怎么认 | 记什么 |
|---|---|---|
| 对外 HTTP | `controller` 包下的 `@RestController`，路径 `/api/bms/...`（管理后台）、`/api/...`（客户端） | 路径、方法、权限注解（`@AuthResource` / `@LoginResource` / 无注解）、调用的 `IXxxApi` 方法 |
| Cloud 远程提供方 | `extends BaseRemoteImpl`，路径 `${easyfk.config.remote.<模块>.base-path:/remote}/...` | 契约 `IXxxRemote`、转发到哪个 Service 方法 |
| Dubbo 提供方 | `extends DubboBaseRemoteImpl`，配合 `ServiceConfig` 导出或 `@DubboService` | 契约、`version` / `group` |
| MQ 消费 | `@RocketMQMessageListener`、`@RabbitListener`、`@KafkaListener` | topic / queue、消费组、处理方法；生产端找 `RocketProducer`、`RabbitProducer` 等 |
| 定时任务 | `@XxlJob("名称")`，常配 `@XxlJobHandler`、`@JobConfig(desc, cron)` | 任务名、描述；`@JobConfig.cron` 只用于初始化，实际周期以调度中心为准，报告里注明 |
| 进程内队列 | 实现 `Processor<T>` 的 Bean；生产端调用 `IngestQueueManager` | 队列名、谁投递、谁消费 |
| Aeron | 订阅 `@AeronTopic`；发送注入 `Producer` | topic、driver、payload 类型 |
| aeron-cluster | 实现 `ClusterStateMachine`（`@ClusterStateMachineBean`）；客户端用 `aeron-cluster-client` | 命令类型、状态、快照 |
| etcd-cluster | `LeaderElection` + `LeaderListener`、`NodeRegistry`、`SharedStore`、`Fence` | 选举名、当选和失主时做什么 |
| WebSocket | `websocket-server` 接入；业务方用 `IPushWsMsgApi` 推送 | 频道、推送对象 |
| 库形态入口 | `AutoConfiguration.imports` 里的配置类注册的 Bean、根包下的模板类或门面接口 | 对外类、开关、可覆盖的 Bean |
| 启动与初始化 | 启动类、`ApplicationRunner` / `CommandLineRunner`、`@PostConstruct`、`SmartLifecycle` | 启动时做了什么业务动作 |

找不到某类入口时不用写；整类入口都没有，也不需要在报告里声明。

## 4. 怎么追

1. **从入口往下读真正被调用的方法**。分支看条件，失败看抛错、返回和提前 return。没走到的调用不画进主图。进入某个模块后，先追它的集群控制（§5），再追业务。
2. **标准 CRUD 归并**：普通业务项目里，一个实体只用了框架基础方法（`ServiceUtil.save` / `delete`、`ConditionUtil` 查询、`BaseApiServiceImpl` 转发）、没有自己的业务判断时，不逐个画流程图。在该模块的「入口」里用一张表列出：实体、表名、对外接口、唯一字段（`@SingleUniqueField` / `@CombUniqueField`）、删除前的关联检查、数据隔离字段、权限资源。只给有业务判断的方法（如取消、审核、结算）写业务描述和画图。
3. **框架调用只写业务决定**：遇到 easyfk 的调用先查 easyfk-framework-skill 和对应模块文档，弄清它在框架里是什么，报告里只写业务上的选择，不把框架内部步骤写成业务步骤。例如：
   - `ServiceUtil.save` →「按主键有则更新、无则新增，订单编号唯一」，不展开框架的唯一性校验过程。
   - `UserDataFiltrationUtil.saasDataFiltration` →「按当前用户的 agentId、merchantId 隔离数据」。
   - `RLockTemplate` →「同一账户按 accountId 加锁」。
   - `@Transactional(rollbackFor = Exception.class)` →「这几步在一个事务里，任一步失败整体回滚」。
4. **判断 `IXxxApi` 是本地还是远程**：Controller 和业务代码只注入 `IXxxApi`，实际实现由依赖的包决定。看调用方所在模块依赖的是 `-server`（`XxxApiServerImpl`，进程内）、`-sc-client` / `-cloud-api`（`XxxApiScImpl`，Feign）还是 `-dubbo-api`（`XxxApiDubboImpl`，Dubbo），再决定画成进程内调用还是跨进程调用。看不出时写「代码中未找到」，不默认是本地调用。
5. **跨进程、跨线程、发消息或等回调**时，把对端当成另一个参与者，注明谁发起。easyfk-thread 线程池、`CompletableFuture`、Disruptor、MQ、Aeron 都算换了参与者或线程。
6. **配置、枚举、常量**只记录这条链路读到的项，`easyfk.config.*` 写全前缀。不把示例数据或别的模块的数据抄进来。
7. **数据与外部依赖**边追边记：读写了哪些表（Entity 的 `@TableName`）、Redis key 前缀、MQ topic、Aeron 通道、Chronicle 文件、调用的外部 HTTP 服务、读到的远程契约。只记代码里出现的，写进架构报告。这些记录同时是 §7.3 业务数据依赖的原料：追完按业务数据归并，不要事后再回头翻代码。

追不到的地方标成「代码中未找到」，不补一个看起来合理的步骤。

## 5. 高可用怎么反推

只写代码里已经实现的控制。代码里看到下面这些，说明的是：

| 代码里看到 | 说明的是 | 要写清 |
|---|---|---|
| etcd-cluster 的 `LeaderElection`、`Fence` | 主备：选主，只有主执行 | 当选和失主时开始、停止做什么；Fence 挡在哪一步前面 |
| aeron-cluster 的 `ClusterStateMachine` | 多副本强一致：leader 处理，follower 回放 | 哪些状态在状态机里、快照和恢复怎么做 |
| lock-redisson 的 `RLockTemplate` | 多实例互斥，不是选主 | 按什么键加锁、拿不到锁时怎么办 |
| XXL-JOB 任务 | 调度中心按路由策略选执行器 | 路由和阻塞策略在调度中心，代码里看不到时写「以调度中心配置为准」；代码读取分片参数时写按分片执行 |
| MQ 消费组 | 同组多实例分摊消费 | 是否顺序消费、消费失败重投后怎么保证幂等 |
| 注册中心 + 无状态 Web 服务 | 多实例对等，靠网关或 Feign 负载均衡 | 只有代码或配置里能看到注册（`registry-nacos` 等）才这样写 |
| chronicle-map / chronicle-queue | 单机持久化，重启后从本地文件恢复 | 不能跨机，换机器数据不在 |
| Aeron 广播、Disruptor 队列 | 不持久化，进程挂掉丢失在途数据 | 丢失后有没有补偿（重放、对账） |

每个模块的高可用按这几项写，没有的项写「代码中未找到」：

- 集群方式：单实例、主备、分片多活，或代码里的其他形态。
- 逻辑控制：谁决定主、成员或分片归属，依据是什么（租约、修订号、静态配置）。
- 故障时：失联、非主、未就绪时本模块停止做什么、继续做什么，由谁接管。
- 与业务流的关系：高可用判断挡在哪一步前面，例如「非主不发」「未就绪不算」。

部署方式（几个实例、怎么扩缩容）多数不在代码里，看不到就写「代码中未找到」，不补一套看起来合理的集群方案。库形态没有自己的进程，写它运行在哪个宿主进程的集群方案里；看不出从属关系就写「代码中未找到」，不把宿主的方案抄成库自己的。

## 6. 重复执行

先看 `docs/reverse/` 里有没有业务分析报告、架构分析报告、业务数据依赖，以及按模块拆出去的文件；业务数据依赖也可能写在 `docs/<项目名>项目说明.md` 里，两处都要看。

- 没有：按 §7 新写。
- 已有报告的文件名不带项目名前缀：先改名补上前缀，并改掉报告之间的链接，再核对内容。
- 已有：对照当前代码核对，不重新生成一份覆盖掉。准确的章节、图和已经对得上的模块保持原样。
- 只改对不上的地方：代码变了、图和调用链不一致、缺了总体流程或整体架构、模块名对不上、高可用写在了业务流程后面。缺的节补上，错的节改正。
- 在改动处注明依据的是哪段代码（类名#方法名）。更新报告开头的「依据」。回复里列出改了哪些节、哪些节核对后未改。

## 7. 产出

| 文档 | 路径 | 写什么 |
|---|---|---|
| 业务分析报告 | `docs/reverse/<项目名>-业务分析报告.md` | 职责、模块、总体流程、调用链，以及每个模块的入口、高可用和业务流程 |
| 架构分析报告 | `docs/reverse/<项目名>-架构分析报告.md` | 系统边界、整体系统架构、技术选型，以及每个子模块的系统架构、数据与外部依赖、配置项 |
| 业务数据依赖 | 有项目说明时写 `docs/<项目名>项目说明.md` 的「业务数据依赖」一节；没有时 `docs/reverse/<项目名>-业务数据依赖.md` | 依赖、自管理、对外提供哪些业务数据，各自从哪来到哪去、谁在用、变了要动哪里。见 §7.3 |

- **项目名**的取法和 easyfk-dev-skill 的 `rules/10-docs.md` §2 一致：Gradle 用 `settings.gradle` 的 `rootProject.name`，Maven 用根 `pom.xml` 的 `artifactId`，都没有时用仓库根目录名。
- 生成的**每份文件名**都以 `<项目名>-` 开头，包括拆出去的报告和图；目录名不加前缀。下文为了简短省略了前缀。
- 两份报告的模块清单、模块名、顺序一致。业务报告里点到的模块，架构报告里要有同名架构；架构报告里的节点，要能在业务报告的调用链里找到。
- 业务数据依赖里的模块名，和两份报告用同一套；表格「使用方」一列能指回业务报告里的模块和入口。
- 图用标准 Mermaid，写在 `mermaid` 代码块里：流程图 `flowchart`，时序图 `sequenceDiagram`，架构图 `flowchart` 加 `subgraph` 框出进程或部署边界。写法和防渲染失败的注意点见 easyfk-dev-skill 的 `rules/10-docs.md` §6。

### 7.1 业务分析报告

```markdown
# <项目> 业务分析报告

> 依据：代码版本 <git 提交短哈希，读不到时写反推日期>；easyfk <版本>

## 总体
### 职责
### 模块
### 总体流程
### 调用链

## 细节
### <模块>
#### 作用
#### 入口
#### 调用链
#### 高可用
#### 业务描述
#### 流程图
#### 时序图

## 与文档的差异
## 未证实
```

- **职责**：项目现在负责什么、不负责什么。
- **模块**：§1 的对照表，加每个模块一句话作用，并指向后面同名的细节小节。只有一个模块时也写这一节，说明它就是整条流程。
- **总体流程**：一张跨模块的业务流程图，模块作为节点，只保留主路径和模块之间的交接。多个参与者、异步或跨进程时，再加一张总体时序图。分支、失败、重试不放进这张图；部署边界写在架构报告里。
- **调用链**：模块之间谁调用谁、走什么方式（进程内、Feign、Dubbo、MQ、Aeron）。每个节点要能指回入口类或对外接口。
- **入口**：这个模块的对外入口表（§3），以及 §4 第 2 条的标准 CRUD 归并表。
- **高可用**：放在业务描述前面，按 §5 写。集群的部署结构画在架构报告里。
- **业务描述**：只写有业务判断的流程，没有的项写「代码中未找到」：
  - 触发：谁、在什么情况下进入。
  - 输入、输出。
  - 业务规则：代码里真正判断的条件。
  - 失败时做什么：抛哪个错误码、回滚什么、是否重试。
  - 不做什么：只写代码里明确拒绝或直接返回的情况。
- **流程图**：模块内部有业务判断的流程，每次都有。先放主路径，关键分支和失败出口放得下就放；挤在一起看不清时，主体图只留主路径，细节拆到 `流程图-<环节>.md`。模块全是标准 CRUD 时写「见入口的归并表」，不画。
- **时序图**：多个参与者、异步或跨进程时画主体流程。进程内一条直线走完的，写「见流程图」。图上每个节点要能指回一个方法或一段配置，指不回的删掉。
- **与文档的差异**：注释、`docs/` 下的需求和设计文档、README 和代码对不上的地方，写清文档怎么说、代码实际怎么做、依据哪段代码。
- **未证实**：只列命名像有、调用链上没找到的点（如有类但没有被任何入口调用、有配置但没有代码读取）。

### 7.2 架构分析报告

```markdown
# <项目> 架构分析报告

> 依据：代码版本 <git 提交短哈希，读不到时写反推日期>；easyfk <版本>

## 总体
### 系统边界
### 整体系统架构
### 技术选型

## 细节
### <模块>
#### 系统架构
#### 数据与外部依赖
#### 配置项

## 未证实
```

先写整体，再写子模块。只有子模块图、没有一张完整的整体架构图，这份报告不算完成。

- **系统边界**：有哪些进程，模块在进程内还是独立部署，模块之间走进程内调用、消息还是远程调用，对外暴露什么（HTTP、Feign、Dubbo、MQ、Aeron）。看不出的写「代码中未找到」。
- **整体系统架构**：一张完整的架构图，模块和进程作为节点，标出调用方向和部署边界，外部中间件（数据库、Redis、MQ、注册中心、调度中心）作为外部节点。只保留主体结构，分支、失败和重试不画。
- **技术选型**：从构建文件读出用了哪些 easyfk 模块和其他关键依赖，每个一句话说明在本项目里做什么用（用 easyfk-framework-skill §4 的能力描述对照），以及形态（easyfk-framework-skill §3 的单体、接口层、微服务、多栈微服务）。
- **子模块系统架构**：把该模块内部的组件、入口和依赖展开成一张图，组件要能指回包、类或配置。普通业务项目按 Controller → Api → Service → Repository 的分层画，不必每个实体画一遍，一层一个节点、标出有哪些实体即可。组件多、一张图看不清时，主体图只留组件和交接，细节拆到 `架构图-<组件>.md`。
- **数据与外部依赖**：§4 第 7 条记下的表、Redis key 前缀、MQ topic、Aeron 通道、Chronicle 文件、外部服务，用表格列出读还是写、在哪个类。
- **配置项**：这个模块读到的关键配置，写全前缀（`easyfk.config.*`、`spring.*`）、作用和代码里的默认值。不抄整份配置文件，不写密码、密钥等敏感值。

### 7.3 业务数据依赖

这份文档回答「这个项目碰了哪些业务数据」，用在业务或需求变更时判断本项目要不要动、动哪里。依赖了行情数据，行情的字段或口径一变，用到它计算的地方都要跟着改；只靠代码检索很难看全，所以单列出来。

#### 先定「业务数据」，不照抄表名

业务数据是业务方一句话能说清的数据集合：行情数据、仓位数据、账户数据、订单数据、持仓数据、商品数据、用户数据、字典数据。**不是**中间件实例、连接池、日志、监控指标、纯技术配置。

按业务语义归并，不按存储方式拆：

- 一个业务数据可能落在多张表、多个 topic、多个接口上，合成一行。
- 一张表也可能只是某个业务数据的一部分，不单独占一行。
- 命名用业务方的说法，不用表名或类名；拿不准时用代码里最接近业务含义的那个词，并在「说明」里写清包含什么。

#### 从代码里找

原料就是 §4 第 7 条边追边记的那些，按来源判断属于哪一类：

| 代码里看到 | 说明是什么 | 记什么 |
|---|---|---|
| Entity 的 `@TableName`、Mapper、Repository | 本项目自管理的数据 | 表名、读还是写 |
| 远程契约调用方：`IXxxRemote`、Feign 到别的服务、Dubbo 引用 | 依赖别人的业务数据 | 契约和方法、取的是哪类数据 |
| MQ 消费（topic、消费组） | 订阅别人的业务数据 | topic、消息里是什么数据 |
| MQ 生产（`RocketProducer` 等） | 对外提供的业务数据 | topic、消息里是什么数据 |
| Aeron 订阅（`@AeronTopic`） | 低时延流式数据，多为行情 | topic、payload 类型 |
| 外部 HTTP（`HttpRequest`、第三方 SDK） | 依赖第三方的业务数据 | 接口、用途 |
| `db-redis` / `cache-redis` 的 key 前缀 | 缓存里的业务数据或共享状态 | key 前缀、用途 |
| `chronicle-map`、etcd `SharedStore`、aeron-cluster 状态机 | 本项目维护的业务状态 | 状态名、用途 |
| 配置项里的外部数据源（库、文件、第三方地址） | 依赖的数据源 | 配置键 |

判断不出是「依赖」还是「管理」的（典型是读了别人写的库表），按代码里有没有写入方定：本项目只读算依赖，有写入算管理，两边都写要注明「双写，归属待确认」。

#### 表格

| 业务数据 | 说明 | 关系 | 来源 / 存储 | 代码位置 | 使用方 | 变更影响 |
|---|---|---|---|---|---|---|

- **关系**：`依赖`（只读，外部或别的系统提供）、`管理`（本项目产生并维护）、`对外提供`（本项目产出、别人消费）。既自管理又对外提供时写「管理，对外提供」。
- **来源 / 存储**：表名、Redis key 前缀、MQ topic、Aeron topic、RPC 契约、外部接口、配置文件，多个用顿号隔开。
- **代码位置**：`包.类#方法`，或模块 / 层，以能指回代码为准。
- **使用方**：本项目里用到它的模块、接口、定时任务、消费端，用两份报告里的模块名。
- **变更影响**：上游定义或口径变了（加字段、改单位、改更新频率、换数据源、停止提供）时，本项目要动的地方。写到模块、接口或 `类#方法`，只能定到环节的写环节。这是全表最值钱的一列，不写「可能受影响」这类空话。

#### 变更关注点

表格之后按数据各写一条，点名最容易漏的联动，格式是「什么变了 → 要动哪里」：

- 行情数据：合约乘数、最小变动价位变了 → 保证金计算（`XxxService#calcMargin`）、涨跌停校验、前端报价推送。
- 仓位数据：可用量口径变了 → 风控拦截、可平量展示、结算。

一句话一条，不复述表格里的内容。

#### 落在哪

按顺序找第一个存在的，改它，不新建第二份：

1. `docs/<项目名>项目说明.md` 存在 → 写 / 改它的「业务数据依赖」一节（还没有这一节时，按 easyfk-dev-skill 的 `rules/10-docs.md` §5 的顺序加在第 4 节之后），其他章节不动。
2. 不存在，但 `docs/reverse/<项目名>-业务数据依赖.md` 存在（上次反推生成的）→ 改这一份。
3. 都不存在 → 新建 `docs/reverse/<项目名>-业务数据依赖.md`。

单独出文档时用这个骨架：

```markdown
# <项目> 业务数据依赖

> 依据：代码版本 <git 提交短哈希，读不到时写反推日期>；easyfk <版本>

## 总览
## 业务数据清单
## 变更关注点
## 未证实
```

- **总览**：依赖几类外部数据、自管理几类、对外提供几类；一句话说清本项目在数据链上的位置（纯消费方、生产方，还是两者都有）。
- **未证实**：配置里有、代码里找不到读取方的数据源；命名像业务数据、调用链上却没人用的表或 topic。写清在哪看到、为什么没确认。

#### 重复执行

已有这份文档时对照当前代码核对，只改对不上的行（新增或删除的数据、换了的来源、变了的调用方），在改动处注明依据的 `类名#方法名`，不重新生成一份覆盖。

### 7.4 拆文件

一个模块的图看不清，或模块很多、总文档过长时，按模块拆开：

- 业务拆到 `docs/reverse/<模块>/<项目名>-<模块>-业务分析报告.md`，架构拆到 `docs/reverse/<模块>/<项目名>-<模块>-架构分析报告.md`。
- 拆出的文件第一行写 `对应：<项目名>-业务分析报告.md 的「细节 / <模块>」`（架构同理）。
- 高可用留在业务总文档该模块的业务流程前面，不拆走。总体流程留在业务总文档，整体系统架构和技术选型留在架构总文档，都不拆走。总文档该模块下留下主体内容并链到拆出的文件。
- 模块内再拆图时，用 `<项目名>-<模块>-流程图-<环节>.md`、`<项目名>-<模块>-时序图-<环节>.md`、`<项目名>-<模块>-架构图-<组件>.md`，第一行写明对应哪份报告、哪个模块、哪一节。细节图里的步骤必须已经在代码里出现。

## 8. 写完自检

1. 两份报告都是先总体后细节；每个模块的高可用在业务描述前面。
2. 两份报告的模块清单、模块名、顺序一致，并和 §1 的对照表一致。
3. 图上每个节点都能指回类、方法或配置；没有代码里不存在的步骤。
4. 跨进程的调用是按依赖判断出来的，不是默认当成本地调用。
5. 框架内部步骤没有写成业务步骤；标准 CRUD 已归并成表。
6. 追不到的地方都标了「代码中未找到」，猜测的点都放进了「未证实」。
7. Mermaid 写法符合 easyfk-dev-skill `rules/10-docs.md` §6，文件名都带项目名前缀。
8. **业务数据依赖**覆盖了 §4 第 7 条追到的表、远程契约、MQ topic、Aeron 通道、外部接口；中间件实例、日志、监控指标没有被当成业务数据。
9. 每份数据的「关系」（依赖 / 管理 / 对外提供）有代码依据，「来源 / 存储」和「代码位置」都能指回去；判断不了的已放进「未证实」。
10. 落在正确位置：有项目说明就写进它的「业务数据依赖」一节，没有才单独出文档；没有和第二份清单重复。
11. 「变更影响」写到了模块、接口或 `类#方法`，没有停在「可能受影响」。

## 9. 回复

先给两份报告和业务数据依赖的路径；业务数据写进项目说明时，给出文件路径和节名。报告已经存在时，先说明核对了哪些节、改了哪些节，不把未改的内容重讲一遍。

新写时：先讲业务总体，有哪些模块、谁调用谁；再按模块讲集群方案和业务流程；然后讲架构，先整体和技术选型，再每个子模块。之后讲业务数据依赖：依赖哪些外部数据、自管理哪些、对外提供哪些，哪几类上游一变就要跟着动。拆开了文件时，列出每份对应哪份报告、哪个模块、哪一节。「与文档的差异」「未证实」单独列出，不混进「已经如此」的描述。
